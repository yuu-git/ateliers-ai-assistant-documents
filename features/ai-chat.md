# AI チャット

## 目的

WinUI 3 の操作感を学びつつ、既に C# コンソールから疎通確認済みの Ollama 通信を再利用して、実用的なチャット機能を完成させる。学習用の使い捨てではなく将来のアシスタント機能として残す。

## MVP の完成条件

- WinUI 3 アプリが起動する。
- Ollama の利用可能モデルを選択できる（モデル一覧取得失敗時の表示も考慮）。
- ユーザーメッセージを送信できる。
- 回答をストリーミング表示できる。
- 複数ターンの会話を継続できる。
- 応答中にキャンセルできる。
- 通信失敗・モデル未起動時に UI が固まらずエラーを表示する。

## 初期 UI

`NavigationView` を用いた左ナビゲーションと、チャットメッセージ一覧、入力欄、送信・キャンセル、モデル選択を基本とする。通知、情報収集、画面監視は将来のナビゲーション候補であり、最初から実装しない。`CommunityToolkit.Mvvm` の採用を検討する。

## 設計

- View / ViewModel に HTTP や Ollama 固有処理を埋め込まない。
- `IChatService` などの Application 契約を経由し、Infrastructure が Ollama を呼ぶ。
- 非同期ストリームを UI スレッドへ安全に反映し、キャンセルを伝播する。
- モデル選択、システム指示、会話履歴の扱いは明示する。
- チャットメッセージと通知は UI 部品を共有できるが、ドメイン概念を無理に同一化しない。

## 段階的な実装

1. WinUI 3 のダミー画面と MVVM バインディング。
2. 既存 C# Ollama 通信のサービス化、単発応答。
3. ストリーミング、会話継続、キャンセル、エラー表示。
4. SQLite による会話履歴保存（次のマイルストーン）。
5. 必要になった段階で API / Worker とプロセス分離。

初期は Desktop からサービスを直接 DI 利用してよい。ただし将来 HTTP API に置き換えられる境界を維持する。

## Phase 1 の決定事項

回答表示は追加要件の [Markdown 回答表示](markdown-display.md) に対応する。本文・送信履歴には Markdown 原文を保持し、変換と WebView2 は Desktop の表示層に配置する。

画像入力の動作確認用に [画像貼り付け](image-paste.md) に対応する。画像はメモリ内で1メッセージ1枚まで保持し、完了した会話の画像も後続の送信に含める。

以下は Phase 1 時点のユーザー確認済み方針。永続化・モデル選択設定・終了確認については後述の Phase 2 方針が優先する。

- `ateliers-learn-llm/src/Ateliers.Learn.LLM/Program.cs` の `HttpClient` と `/api/chat` 呼び出しを再利用し、Infrastructure の `OllamaChatService` に移植する。モデル一覧は `GET /api/tags`、生成は `POST /api/chat` の NDJSON ストリームを使う。
- 接続先は `http://localhost:11434`。取得したモデル一覧から利用者が明示的に選択する。モデルの自動ダウンロードは行わない。一覧の再取得では、まだ利用可能なら選択を維持する。
- 独自のシステム指示は追加しない。モデル固有の生成オプションは変更せず、回答本文を表示する。`thinking` は本文や次回の履歴へ混ぜない。
- 次回のリクエストは、この起動中の会話で完了したユーザー・Assistant の送受信と今回の入力で構成する。アプリ側の自動切り詰めは行わない。モデルのコンテキスト上限や Ollama 側の切り詰めは、この方針で解消されるものではない。
- 中止・失敗した送受信は、部分応答を含め画面に状態付きで残す。そのターンのユーザー入力と Assistant 応答は両方とも次回の送信履歴から除外する。
- モデル変更で会話を引き継ぐ。各メッセージには送信時のモデルを表示する。「新しい会話」で表示と送信履歴をリセットし、モデル選択は維持する。
- Phase 1 追加要件として、チャット送信にも `keep_alive: -1` を指定する。起動・停止、選択変更と終了時のモデル解放は [モデル管理](model-management.md) の単一チャット用方針に従う。
- 設定・モデル選択・会話は終了時に破棄する。入力欄の Enter は改行、送信はボタンで行う。

### 実装上の待機・失敗の扱い

- 一覧取得は 10 秒、回答は既存の試験コードと同じく全体で 10 分を期限とする。回答の期限はストリーム本文の待機にも適用する。
- 送信中はモデル変更・入力・一覧更新・新しい会話・二重送信を無効にし、中止だけを有効にする。画面は応答し続ける。一覧取得中も非同期で待機する。
- 通信失敗、HTTP エラー、異常な JSON、完了通知のない切断、空の回答をエラーとして表示する。モデル一覧の空と取得失敗は区別する。自動再試行は行わず、一覧更新や再送信を利用者が行える状態へ戻す。
- ウィンドウ終了で実行中の処理をキャンセルする。例外詳細は `Trace` に出力し、ファイルログの永続化は後続で扱う。

API 仕様の参照先: [チャット](https://docs.ollama.com/api/chat)、[モデル一覧](https://docs.ollama.com/api/tags)、[ストリーミング](https://docs.ollama.com/api/streaming)。

## Phase 2 の決定事項

- [保存方針](../data-storage-policy.md) と [実装指示](../phase2-codex-implementation-instructions.md) に従い、新規会話はメモリ上で開始し「会話を保存」でタイトルを指定して SQLite へ保存する。保存済み会話の一覧はチャット内部に置く。
- 原文・モデル・日時・メッセージ順・表示状態・送信履歴への採否と、送信済み画像・未送信の入力・添付を復元する。画像は縮小済み PNG の BLOB とする。
- 中止・失敗ターンは表示に残して保存するが、復元後も送信履歴には含めない。モデル変更による会話引き継ぎと画像制約は維持する。
- 保存済み会話への応答追加は完了・中止・失敗時、下書き変更は遅延集約して自動保存する。失敗時は未保存の変更として通知し、内容をメモリ上に維持する。
- 新しい会話・別会話・画面離脱・終了で変更が失われる場合は保存／破棄／キャンセルを確認する。保存済みの未反映変更は先に保存を試み、失敗した場合にも確認を行う。
- 最後のモデル選択だけを Roaming JSON へ保存する。存在するモデルなら起動時に選択を復元し、自動ロードしない。保存モデルが存在しない会話を開いた場合はモデルを未選択にして通知する。
- 削除確認後、保存済みスレッドとメッセージ・画像を削除する。個別メッセージの編集・削除や自動削除は行わない。
