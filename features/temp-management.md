# アプリ専用 Temp 管理

**複数監視での共有:** MVP 完了後の [複数画面監視](multi-screen-monitoring.md) でも `CapturedImageStore` は Worker 全体で一つとし、監視ごとの別ストアによって128 MiB上限を倍増させない。各監視のセッション／対象IDとリースを分離し、上限超過で他の使用中画像を削除しない。現在画像1枚の解析後に解放・削除し、ディスク Temp の上限・所有者契約も変更しない。

2026-10-30。Phase 6 完了後、Phase 7 に向けた横断改善として追加した。[実装指示](../ai-implementation/temp-management-codex-instructions.md) と利用者が承認した設計を基にする。新フェーズは追加せず、定期監視・画像差分・音声・複数画像の Ollama 送信は実装しない。

**Phase 7 の利用開始:** [継続画面監視](phase7-implementation-status.md) は、この基盤の `CapturedImageStore` へ現在画像をセッション／対象 ID・実取得時刻で登録し、一枚リースで解析後、解放・削除する。定期監視を Temp 基盤自体へ追加したものではなく、複数画像同時送信・画像差分・ファイル退避は導入しない。以下の Temp 管理導入時の上限・安全性・検証記録は維持する。

## 既存機能への影響

Phase 6 のキャプチャは従来どおり一枚をメモリ内で保持する。既存画面を履歴 UI に変更せず、Temp への自動書き出しや、メモリ不足時のディスク退避は行わない。画像ストアとファイルストアは、将来の制御処理から利用できる基盤として提供する。保存済み会話の画像 BLOB、記事 Markdown、ログ、WebView2 のユーザーデータ／キャッシュは別管理で、今回の削除対象に含めない。

## パスと所有者

`IApplicationPaths.TempDirectory` と `AppDataPaths` を再利用する。Release の実パスは次の構成で、Debug は `Ai-Assistant.Debug` に分離する。参照・起動だけで不要なフォルダーを作らない。

```text
%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\temp\v1\
  manager.lock
  <プロセス起動ごとの所有者GUID>\
    owner.lock
    capture\
    audio\
    work\
```

用途フォルダーは最初のファイル生成時に必要なものだけを作る。Audio の用途識別は音声機能の実装を意味しない。ファイル名は GUID・確定時刻 UTC・整合性確認用 SHA-256 だけで、ウィンドウ名、プロンプト、画面テキストを含めない。

- `manager.lock` は同じ Debug／Release 環境内の予約・確定・清掃を直列化する。取得期限は3秒。
- `owner.lock` を OS ハンドルで保持し、生存中所有者を判定する。PID・ファイルの古さだけでは判断しない。生成・公開も環境の排他内で行う。
- プロセスをまたぐ一時データの受け渡しは提供しない。同じアプリを複数起動した場合も別所有者とする。
- 他の生存中所有者は、非使用中に見えるファイルも含めて回収しない。UI 終了を理由に共有ルートを削除しない。
- 所有者が終了してロック取得可能になった領域は、期限を待たず、認識できる管理ファイルを次回清掃で回収する。強制終了時も OS がハンドルを解放する。使用中の外部ハンドル等で削除できなければ残してログへ記録する。

## メモリ内の複数時点画像

Application の `CapturedImageStore` が、キャプチャ ID、セッション ID、対象 ID、実取得日時 UTC、寸法・容量、正規化済み `ChatImage` を扱う。識別子は GUID で、表示名・PID を代用しない。画像は不変のメモリ参照を共有し、列挙時は画像本体を含まないメタデータだけを返す。

- 時刻順の列挙、ID 指定の一括取得、許容時間差付きの近傍時刻選択を提供する。
- 近傍選択で等距離なら過去側を優先する。指定した複数時点に同じ画像しか選べない場合は不足とする。30秒などの固定間隔を前提にしない。
- 同一セッション・対象の全画像を確保できた時だけ `CaptureBatchLease` を返す。別対象・不足・期限外では全件失敗し、部分的な参照数を残さない。
- `using` により解析完了・例外・キャンセル時に全件を解放する。使用中の画像は期限が過ぎても既存リースから利用できるが、新規取得の候補にはしない。
- 明示削除は非使用中だけに許可する。リース外で画像参照を保持し続けないことは呼び出し元の契約とする。
- メモリは不変画像を保持するためファイル消失は起こらない。画像のデコード・正規化は既存の入力側の責務。ディスクの消失・破損は次節のファイルストアで扱う。

## ディスク一時データの確定と使用権

Infrastructure の `TempFileStore` が `ITempFileStore` を実装する。利用者や外部コンテンツから任意パスを受け取らず、内部生成した ID と用途で操作する。入力ストリームを閉じる責務は呼び出し元に残す。

1. 作成前に最大バイト数を宣言し、環境のロック内で容量・件数を予約する。予約は `<ID>.reserve` に記録する。
2. `<ID>.part` に上限を確認しながら書き込み、フラッシュ・クローズする。途中失敗・キャンセルでは予約と未完成データを回収する。
3. 同じロック内で `<UTC ticks>_<ID>_<SHA256>.bin` という空の確定マーカーを作る。予約を除去し、読み取り使用権を取得する。本体は `.part` のままで、マーカーがなければ未完成として扱う。
4. 確定したデータだけを ID 指定で取得する。SHA-256 と確定情報を検証し、破損・消失・別所有者・期限外の場合は全件失敗させる。途中取得したハンドルも解放する。

ディレクトリ固定を緩めるリネームや二重コピーは使わない。確定マーカーは `CreateNew` で原子的に作成し、未完成データを読み取り対象にしない。確定時刻はファイルの保持期限用で、画像の実取得時刻とは別である。

`TempFileBatchLease` は読み取り専用ストリームと親ディレクトリの固定を保持する。使用中は削除・書き換えず、明示削除も false を返す。解放後に清掃を要求する。取得のキャンセル・例外では一括して戻し、画像データやストリームをリース外へ持ち出さない。

## 保持上限と上限超過

| 対象 | 件数／世代 | 保持期間 | 容量 |
| --- | --- | --- | --- |
| メモリ内画像 | セッションごと最大64枚 | 実取得時刻から5分 | プロセス全体128 MiB |
| ディスク一時データ | 環境全体最大64件 | 確定時刻から30分 | 同一環境の UI／Worker 合計256 MiB |

初期案の確認用計測では、検証用ウィンドウの画像は626×393px・約12 KiBだった。実画面・ゲームの代表値とはみなさない。最大 PNG は既存入力の12 MiB制限を維持する。メモリの計上は PNG サイズだけでなく、Base64 UTF-16 文字列と一件512バイトの管理情報概算を含む。プレビュー・デコード・送信時の一時コピーやプロセス全体のメモリを128 MiBに制限するものではない。

ディスク容量は本体の論理バイト数と書き込み予約を計上する。空の確定マーカーやロック、ファイルシステムの管理領域・クラスタ単位の割り当ては別。件数は本体とマーカーを合わせて一件、予約中も一件として数え、`.part` と予約分を二重計上しない。管理する所有者の用途ディレクトリ内では、認識できないファイルも容量へ計上し、判断不能な場合は新規生成を失敗させる。用途外・認識外ディレクトリは走査せず、管理容量の対象にも含めない。

保持期間・件数・容量を併用し、古い非使用中データから回収する。使用中を強制削除せず、回収不能なら `TempStorageException` で新規生成・登録を失敗させ、診断を記録する。他の生存中所有者の不要データを強制回収しないため、合計に余地がない場合は、その所有者の解放・清掃を待つ。

`CaptureRetentionPolicy`／`TempRetentionPolicy` をホストから指定できる。設定 UI・Roaming 設定は追加しない。同じ環境のホストには同じディスクポリシーを指定する。音声の実際の保持量・世代幅は機能導入時に見直す。

Capture は原則メモリ優先で、ディスクが必要になった場合だけファイルポリシーを使う。Audio／Work もディスク側の同じ初期ポリシーを共有し、用途ごとに256 MiBずつ確保する方式ではない。

## 清掃契機と終了

- UI／Worker の起動時、ファイル作成前、処理完了・使用権解放時、明示清掃、通常終了時。
- 専用の定期タイマーは追加しない。保持期限は次の清掃契機で適用する。継続監視のメンテナンス周期は Phase 7 の論点。
- UI の起動時清掃は背景で実行する。Worker の起動待ちと両ホストの終了待ちは最大3秒。失敗・時間切れでも既存機能や終了を妨げない。
- 重なった清掃は一つに集約する。終了要求は新しい生成・取得を禁止し、進行中の書き込みへ中止を通知する。既存リースが残っている間は所有者ロックを維持する。
- 中止を無視する入力や強制終了で処理が完了しない場合は、OS によるハンドル解放後、次回起動で回収する。清掃の永久再試行はしない。
- 制御用の空ロック・空ディレクトリが正常終了後に残る場合があり、次の別所有者による清掃で回収する。共有ルートの一括削除はしない。

## 削除範囲とプライバシー

`ITempFileSystem` を I/O 境界とし、実装の `SafeTempFileSystem` が絶対パス・配下判定、再解析ポイント・ハードリンク拒否、ディレクトリ差し替え防止、検証したハンドルでの個別削除を担当する。実操作中に祖先を検査・固定し、長寿命の使用権では Temp 内だけを固定する。長い AppData パスも Win32 の拡張長パスで開く。

認識外のファイル・ディレクトリ、再解析ポイントを削除・追跡しない。安全性不明・I/O 失敗はログへ記録し、無理に清掃しない。保存先を再解析ポイントで置き換えた環境は対応対象にしない。ACL は既存ユーザープロファイルから継承し、公開・共有権限を追加しない。

ログは既存 `IAppDiagnostics` の固定操作識別子・例外型・コードだけを使い、画像・Base64・対象名・本文・パス・ファイルハッシュを出力しない。安全な操作方法は [Microsoft の再解析ポイント資料](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations) も参照した。

## Phase 7 に残すもの

キャプチャの自動登録、監視セッションの開始・終了、取得周期・画像比較、実際の履歴幅の調整、複数画像を含む Ollama 契約、コメント UI、Worker／Capture Agent 間で共有が必要になった場合の設計。今回はスケジューラ・音声再生や、プロセスをまたぐ使用権へ拡張しない。
