## 1. 目的と基本方針

AI チャットは **Ollama 上のローカル LLM の動作確認・性能比較・プロンプト検証**を行うための補助機能である。ChatGPT や Claude のような汎用 AI チャット製品を目指さない。

- テキストモデルと画像認識モデルを手軽に試せることを優先する。
- チャットの機能追加よりも、Web 情報収集・画面監視などアシスタント本来の機能を優先する。
- Ollama 通信や画像送信など、他機能でも使える処理は UI に依存させない。
- 新しい要求が生じても、まず「チャット画面に必要か」「共通基盤または別機能に置くべきか」を判断する。
- 本文は共有された実装報告と画面確認に基づき、今回、関連する通信・ViewModel・表示・貼り付け・モデル管理のコードと照合した。ソースコード全体の独立レビューや安全性監査の結果ではない。

ここでいう「性能比較」は、モデルを選び直して応答を手動で比較する用途を指す。応答時間・tokens/s・GPU 使用率などの測定、比較結果の保存、自動ベンチマークは実装していない。

- Markdown 対応時: 自動テスト **21 シナリオ**成功。x64 Debug ビルド成功。実 WebView2 による書式・コード表示・逐次更新・中止・失敗・リンク制限・スクロール等を確認。trimming 済み Release で送受信・モデル管理・終了時アンロードを確認。
- 画像貼り付け対応後: 自動テスト **26 シナリオ**成功。Debug ビルド成功（警告・エラー 0）、Release 発行成功。`gemma3:4b` による画像のみの送信と後続会話を実機確認。既存機能の回帰テスト成功。
- Phase 2（2026-10-29）: 自動検証は Debug / Release とも **35 シナリオ**成功。実 SQLite、画像 BLOB・下書き、競合・保存失敗、設定とログを追加確認。Debug / Release の Unpackaged 実画面で保存・再起動・復元・削除を確認。Release は trimming 無効へ変更し、クリーン発行物で起動・設定・Explorer 起動を確認した。MSIX の固定パスは Debug の一時開発パッケージで確認し、Release MSIX・Store 配布等は未検証。

主な関連要素: `ChatTranscriptView`、`MarkdownMessageRenderer`、`TranscriptProtocol`、`ChatImage`、`ClipboardImageService`、`ClipboardImageController`、`ChatViewModel`、`ModelManagementViewModel`、`ChatModelSession`、`OllamaChatService`。実装の詳細と最新のテスト手順はアプリケーション側の `README.md`、機能別の判断は [Markdown 表示](markdown-display.md)・[画像貼り付け](image-paste.md)・[モデル管理](model-management.md) を参照する。

### 2.2 会話・接続の補足仕様

- 接続先は `http://localhost:11434` 固定。`GET /api/tags` で取得したモデルを利用者が選ぶ。接続先設定 UI、独自のシステム指示、生成オプションの編集は実装していない。`thinking` は回答本文や送信履歴に含めない。
- 次回の送信は、完了したユーザー・Assistant の全ターンと今回の入力で構成する。中止・失敗したターンはユーザー入力・部分応答・画像を画面に残すが、そのターン全体を次回の送信履歴から除外する。
- アプリ側の履歴切り詰め、要約、トークン数管理はない。Ollama やモデルのコンテキスト上限の影響は残る。
- モデル変更時はテキスト・画像を含む会話を引き継ぐ。新しく選んだモデルは選択だけではロードしないが、起動ボタンまたはチャット送信によってロードされる。「新しい会話」は入力・添付・表示・送信履歴を消し、モデル選択を維持する。
- 送信・モデル変更・モデル操作の競合を制御する。送信中は入力・モデル変更・新しい会話などを無効にし、生成の中止を可能にする。送信はボタンで行い、Enter は改行。
- モデル一覧取得は10秒、回答全体は10分を期限とする。接続・読み取り・応答形式の失敗はエラーにし、自動再試行しない。Phase 2 では明示保存した会話と下書き、および最後のモデル選択だけを永続化する。保存しない場合の終了・離脱には確認を設ける。

## 4. 現行制約と再検討の条件

| 現行仕様・制約 | 現時点の判断 | 再検討のきっかけ・方向性 |
| --- | --- | --- |
| **画像の長辺は最大 1536px** | 初期値として妥当。通信量と推論負荷を抑えやすい | 細かな文字・UI・設備が読めない場合。画像サイズの設定化、切り出し、対象領域ごとの送信を比較検討する |
| **1 メッセージにつき画像 1 枚** | 画像認識の単体検証には十分 | 複数フレーム比較、複数画面の状況把握が必要になった場合 |
| **新規会話は明示保存までメモリ内で扱う** | 保存した会話だけを SQLite に残す。保存済みの追記と下書きは自動保存 | 保存期間・自動削除・大量画像・バックアップの要求が具体化した場合に再検討 |
| **完了したターンの画像は後続リクエストで毎回再送信する** | 文脈を保つために有効。会話全体の画像数に上限や自動削減はない | 画像数や会話長の増加で遅延・メモリ負荷が問題になった場合。古い画像の除外や会話リセットを検討する |
| **画像対応モデルの判定なし** | 利用者の運用で対応可能 | 非対応モデルへの誤送信が頻発した場合。モデル能力の取得・表示を検討する |
| **Markdown 表示の更新間隔は約 100ms** | 逐次表示と描画負荷のバランスが良い初期値 | 表示遅延・CPU 使用率・ちらつきが目立つ場合。測定して調整する |
| **WebView2 は会話領域に 1 インスタンス** | 現状の適切な構成 | 長い会話で DOM が肥大化した場合。段階表示や DOM 仮想化を検討する |
| **受信中のコードは着色せずプレーン表示** | 完了・中止・失敗時に対応言語を着色できれば検証用途に十分 | 長いコード生成中の可読性が問題になった場合に検討する |
| **外部画像・数式・Mermaid は非対応** | 現行の表示要件では不要 | 実際のモデル出力で継続的な不便が生じた場合に個別検討する |
| **通常終了時に管理対象モデルのアンロードを試みる** | 終了時の解放処理は5秒、ウィンドウ側の待機は最大6秒。通信失敗時も終了を妨げない | 常駐処理や複数機能によるモデル共有が始まった場合。利用者・利用中状態を一元管理する |
| **モデル変更時に管理対象の旧モデルをアンロード** | 単一のチャット用モデルを扱う現状では合理的。失敗は通知し、自動で新モデルをロードしない | 画面監視・情報収集などが同じモデルを同時使用する場合。利用中モデルを無条件に停止しない設計に変更する |
| **外部ブラウザーの実起動は自動テストで差し替え** | テストの独立性の観点では合理的 | リリース前に実環境でリンク操作を手動確認する |
| **WebView2 障害時は原文表示へ切り替える** | チャット操作を継続する。自動再初期化はなく、履歴の添付画像はサイズのテキスト表示になる | Markdown・画像表示を復旧する場合は再起動。自動復旧が必要になれば検討する |

### 4.1 将来の画面解析で特に注意する点

Factorio など細かな情報を含むゲーム画面では、全画面を一律に 1536px へ縮小すると、アイコン・数値・設備状態の識別精度が落ちる可能性がある。画面監視機能を開発する際は、**画像全体の縮小**と**対象領域の切り出し**を比較し、推論速度・精度・VRAM 使用量を実測する。現時点ではチャット側に画像編集 UI を追加しない。

### 4.2 モデル共有に関する注意

Ollama の `/api/ps` はサーバー全体のロード状態を示すもので、モデルのロード元アプリケーションを識別しない。**モデル変更時・通常終了時の自動アンロード**だけを、アプリ側で追跡する管理対象モデルに限定する。一覧に表示された全モデルを管理対象へ取り込むことはない。

一方、チャット画面の「停止」とモデル管理画面での**明示的な手動停止**は、選択したロード済みモデルを停止する。管理対象でないモデルも停止できるため、他アプリがロードしたモデルを選んで停止することも可能である。

`ChatModelSession` は、明示ロードまたはチャット使用を要求した時点で、失敗・中止の場合も含めてモデルを追跡する。すでに他アプリがロードしていたモデルでも、本アプリで使用すれば管理対象になり得る。したがって、管理対象の追跡は排他的な所有権や他アプリへの無影響を保証しない。

ロード要求・チャット送信では `keep_alive: -1`、停止要求では空の `messages` と `keep_alive: 0` を使用する。強制終了・クラッシュ・停止時の通信失敗では、モデルがロードされたまま残る場合がある。将来、常駐サービスや複数の AI 機能が並行稼働する段階では、モデルの所有・利用・アンロード方針を再設計する。

## 5. 機能追加の判断基準

新しい提案が出た場合は、以下を順に確認する。

1. **目的適合**: ローカルモデルの動作確認・性能比較・プロンプト検証に必要か。
2. **配置先**: チャット UI ではなく、Web 情報収集・画面監視・共通サービスに置くべき機能ではないか。
3. **実害の有無**: 現行制約による具体的な不便・不具合・測定結果があるか。
4. **影響範囲**: MVVM、会話履歴、Ollama 通信、モデル管理、WebView2 の安全性を維持できるか。
5. **検証可能性**: テスト条件・成功基準・回帰確認を定義できるか。

原則として、**具体的な必要性が確認されるまでチャット機能の追加開発は行わない**。不具合修正、依存関係の安全性対応、他機能での共通基盤再利用はこの限りではない。

## 7. 現時点の結論

- **AI チャットの現行スコープは完了**とする。
- Markdown 表示と画像貼り付けにより、テキスト・画像の両方でローカル LLM の動作確認が可能になった。
- 見送り項目は開発漏れではなく、用途を限定するための意図的な判断である。
- 制約は直ちに解消せず、利用上の問題や新しい機能要件が具体化したときに再検討する。
- 次の開発は既存ロードマップに沿って進め、チャット機能の高機能化を優先しない。

## 8. クリップボード貼り付け時のクラッシュ対策（2026-10-28）

**発生事象**

テキストおよび画像の Ctrl+V による貼り付け操作中、断続的にアプリケーションがクラッシュした。

**調査結果**

Windows のクラッシュログに2件の同種の XAML 例外が記録されていた。

`Paste` イベント内で直接 `Clipboard.GetContent()` を呼び出す処理が、WinUI の既知の問題と整合していた。ただし、原因の完全な特定には至っていない。

**実施した対策**

- クリップボードの読み取りを Paste イベント終了後に延期
- 複数の貼り付け処理を順序制御
- 古い非同期結果が編集内容や破棄済み画面へ反映されることを防止
- 選択範囲置換、Undo、改行などの既存編集機能を維持

**検証結果**

- Debug / Unpackaged の実画面検証を5回実行し、合計500回のクリップボード読み取りでクラッシュなし（改修途中の99回を4回、最終版の104回を1回）
- 検証は `TextBox.PasteFromClipboard()` でネイティブの Paste イベントを発生させたもの。物理的な Ctrl+V の500回操作や、MSIX 版・すべての外部アプリのクリップボード提供元を網羅した検証ではない
- 選択範囲・改行・カーソル・Undo・文字数上限、テキスト50回と画像5回のキュー投入、画像／テキスト20回の交互貼り付け、遅延提供元・不正画像・破棄時の競合を確認。クリップボードは検証後に復元
- 既存の自動テスト26シナリオ成功
- Debug / Release ビルド成功

**今後の方針**

現時点では対策済みとして扱う。ただし、断続的な不具合であり、完全な再発防止を保証するものではない。

再発時はクラッシュログとダンプを取得し、今回の事象との同一性を確認する。
