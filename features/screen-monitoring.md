# 画面監視とゲームアシスタント

## 構想

利用者が明示的に指定した画面・ウィンドウを Vision 対応ローカル LLM で解析する。Factorio、FF14 などのゲームに加え、一般的なデスクトップ作業も対象となり得る。特定アプリ専用の高度な助言やコメント品質の保証は初期 MVP の必須要件としない。

2026-10-30 の [ロードマップ](../roadmap.md) 更新により、手動解析を Phase 6、継続監視を Phase 7 に分けた。Phase 6 は実装・開発検証に続き、利用者から機能実装の完了確認を受けて完了した。Phase 7 は未実装。Phase 7 完了をアプリケーションの初期 MVP 到達点とし、音声は時期未定の別構想へ移した。

**完了後の横断改善:** [アプリ専用 Temp 管理](temp-management.md) と複数時点画像のメモリ保持・一括使用権を追加した。Phase 6 の画像は従来どおりメモリ内の一枚だけで、ファイル保存や履歴 UI へ変更しない。将来の監視制御から利用する基盤であり、複数画像の Ollama 送信や定期登録は未実装。

## Phase 6: 手動キャプチャ・Vision 解析 MVP（範囲と実装）

対象選択 → 手動キャプチャ → 画像プレビュー → 既存 Ollama 画像入力を活かした Vision 解析 → 結果表示を一連で操作できることを完了条件とする。基本的なエラー処理を含め、継続監視にも再利用できるよう責務を分ける。定期キャプチャ、継続監視、自動コメント投稿、音声、高度な画像差分、長期コンテキスト管理は対象外。

### 実装した操作（2026-10-30）

1. ナビゲーションの「画面解析」を開く。
2. 「対象を選択」で Windows 標準 Picker からディスプレイまたはウィンドウを選ぶ。対象名は OS の `DisplayName` を表示し、種類は推測しない。キャンセルでは既存の対象・画像を維持する。
3. 「キャプチャ」を押して一枚取得し、プレビューと送信画像の画素数を確認する。選択だけでは取得しない。取得失敗では直前のプレビューを保持するため、エラー表示と画像を確認して再取得する。
4. 編集可能な一般的な画面説明プロンプトと、導入済みの画像入力対応モデルを指定して「解析」を押す。モデル名による能力判定は行わず、非対応時は Ollama の API エラーを表示する。
5. Markdown のストリーミング結果を確認する。「中止」で部分応答を保持し、「画像と結果を破棄」でメモリから外す。今回の結果のみを表示し、次回送信へ履歴を追加しない。

モデル選択だけではロード・停止しない。解析操作でモデルがロードされる場合があり、既存 `ChatModelSession` の管理対象追跡・排他・通常終了時解放を共有する。既存 AI チャットの用途、履歴、選択設定は変更しない。

### AI 停止・資源制御（承認済み）

AI 一時停止中、Worker 未接続・版不一致などで状態を確認できない場合は解析しない。対象選択・キャプチャは利用できる。既存 UI の状態更新で一時停止または未接続を検知した場合、解析へ中止を通知する。ポーリングは既存の約5秒周期を共有するため、外部からの変更は検知まで遅れる場合がある。

実行時は共有モデルの排他権取得後に Worker の状態を API で再確認し、停止中なら Ollama に送信しない。Worker の自動ロード設定は変更しない。バックグラウンド処理と排他が競合した場合は完了後に再試行する。通常環境に旧 Worker が残っている場合は、設定画面で停止後に現在のアプリから起動し直す。

### 採用方式と責務

- Application の `IScreenCaptureService` は OS に依存しない画像取得境界、`ScreenAnalysisService` は既存 `IChatService` と `IModelWorkCoordinator` を使った今回の画像一枚の解析を担当する。
- Desktop の `WindowsScreenCaptureService` は `GraphicsCapturePicker` を HWND で初期化し、WGC と BGRA 対応 D3D11 デバイス、`CreateFreeThreaded` のフレームプールから一枚取得する。フレーム到着イベントでは GPU コピーを待たず、別の非同期継続で `SoftwareBitmap` にコピーする。
- 取得期限は10秒。フレーム・プール・セッション・デバイス・生 COM 参照を操作ごとに解放する。取得中のサイズ変更は余白を除去するか、拡大時は再取得を案内する。
- 既存の画像正規化を再利用し、元画像は4000万画素・PNG は32 MiBを上限とする。縦横比を維持して長辺1536px以下、送信 PNG は12 MiB以下にする。縮小後の同じ PNG をプレビューと送信へ渡し、プレビューのデコード完了前は解析を許可しない。
- `ScreenAnalysisViewModel` は操作状態・画像・結果を保持し、表示側の `ScreenAnalysisView` がプレビューをデコードする。旧プレビュー・遅い解析コールバックが次の画像・結果を上書きしないようにする。
- Markdown は既存 `ChatTranscriptView` 一つを使い、安全化・コード着色・約100msの描画集約を再利用する。広幅は横配置、狭幅は入力と結果を縦配置する。
- 画像・プロンプト・応答・対象名を診断ログへ追加しない。画像と結果は画面を切り替えてもアプリのメモリ内に保持し、終了時に破棄する。DB・履歴・ファイル保存・Migration・Worker の収集処理は追加しない。

標準 Picker の HWND 初期化と WGC は [Microsoft のキャプチャ資料](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)、MSIX の `graphicsCapture` 宣言は [Capability 資料](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/app-capability-declarations) に従う。Debug／Release の両マニフェストへ宣言を追加し、borderless／programmatic の権限は追加しない。

### 検証と制約

Debug／Release の x64 Unpackaged ビルド、両構成の全83件（既存80件＋専用3件）のテストが成功。既存の `NU1900`（NuGet 脆弱性情報取得失敗）警告は残る。専用の `ScreenAnalysisTests` は、同じ画像の送信、選択キャンセル、過去結果の分離、取得失敗、部分応答、解析中止、対象終了、終了待機、排他取得後の停止再確認を検証する。

既存の `Verify-WorkerDisplay.ps1 -GitHub`／`-Notifications` と `Verify-UiRefactoring.ps1` も成功。実 WinUI・独立 Worker の取得・通知・未読／ブックマーク／タグ・単体／一括削除・ログ・チャット独立性・Markdown・複数幅レイアウトを回帰確認した。既存の実モデルチャット全操作を改めて手動操作したことは意味しない。

実キャプチャの明示検証は次のコマンドで実行する。Debug のみで有効な診断ホストを使用し、画像をファイルへ保存しない。

```powershell
pwsh -File tests/Verify-ScreenAnalysis.ps1
pwsh -File tests/Verify-ScreenAnalysis.ps1 -Model gemma3:4b
```

標準 Picker とは区別し、診断専用の `CreateForWindow`／`CreateForMonitor` で既知の検証対象を選択して、通常の取得サービスでフレームを取得する。ウィンドウ・ディスプレイ取得、PNG プレビュー、Markdown・コード着色、横／縦配置、18回の反復取得、対象終了を確認した。ウォームアップ後の検証上限（ハンドル増加80・private memory増加256 MiB）以内であり、無制限の連続動作を保証する試験ではない。

実 `gemma3:4b` から検証用ウィンドウ画像への Vision 応答を確認した。実モデル検証には一時領域の同版 Worker と既存モデル排他を使い、AI 停止状態を API で確認する。通常環境の旧 Worker は変更していない。ディスプレイ画像は Ollama へ送らず、画像・応答本文を検証ログへ出力しない。

### 導入時の手動確認手順と環境別制約

- 通常 UI の標準 Picker で一般ウィンドウ／ディスプレイをそれぞれ選択し、対象名・キャンセル・プレビュー・解析を確認する。自動検証は Picker 操作そのものを代替しない。
- AI 一時停止中／Worker 停止中は解析できず、対象選択・取得は可能であることを確認する。設定の未保存値ではなく実状態に従う。
- 対象終了、最小化・画面ロック、Ollama 停止、非対応モデル、解析中止を通常 UI で確認する。失敗時に直前の画像・部分応答が残ることを理解して操作する。
- 保護コンテンツ・一部の排他フルスクリーンゲームは取得を保証しない。HDR の色再現・色変換、複数 GPU／DPI、MSIX 配布形態は未検証。
- 自分のウィンドウやディスプレイを選ぶとプレビュー自身が映り込む場合がある。自動連鎖はしないが、必要なら表示位置や対象を変更する。

2026-10-30 に利用者から機能実装の完了確認を受けた。自動検証は標準 Picker の実操作を代替しておらず、配布形態・OS・DPI 等の全組み合わせを検証済みとは扱わない。上記は導入時の確認手順と、引き続き残る環境別の制約である。

## Phase 7: 継続監視・AI コメント MVP（暫定計画）

指定対象の監視を明示的に開始・停止・再開し、設定間隔と実際の処理能力に応じてキャプチャ・解析して、コメントを Slack / Teams に近い時系列チャット形式で表示することを暫定完了条件とする。監視中の可視化、ジョブを無制限に積み上げない制御、既存 AI 一時停止・資源制御との整合性を扱う。

UI を閉じた際の動作、既存 Worker／別 Capture Agent の採否、最小化・ロック・対象消失、解析頻度・負荷制御の具体値は Phase 6 の実測後、Phase 7 の実装指示作成時に決める。高度な差分・意味的イベント検出、ゲーム専用認識、音声生成、外部アプリの自動操作、無制限の会話コンテキストは対象外。

## 責務とプロセス

- 画面キャプチャは **ユーザーセッション側** の Windows プロセスで実行する。
- `Windows.Graphics.Capture` を第一候補とし、対象ウィンドウまたはディスプレイを選択する。API の採用と制約は Phase 6 の調査で確認する。
- Windows Service にデスクトップキャプチャを直接担当させない。
- WinUI 3 ウィンドウを閉じても監視を続けたい場合、ユーザーセッション常駐 Agent の独立を検討する。

## 初期 MVP 後も含む処理の構想（未確定）

以下は長期的な候補であり、変化判定、長期的な比較、コメント必要性判定、音声を Phase 6・7 の必須処理とするものではない。

```text
監視 ON -> 対象選択 -> 定期キャプチャ
  -> 縮小・圧縮・変化判定
  -> Vision LLM 解析
  -> 過去の状況・発話と比較
  -> コメント必要性の判定
  -> 通知 / 音声（任意）
```

キャプチャ周期と推論周期を分けて扱う必要性は Phase 7 で検討する。ゲームは常時動くため単純な画像差分ではノイズが多く、ROI、閾値、クールダウン等は後続候補とする。音声の発話周期は時期未定の [音声出力基盤](media-integration.md) で検討する。

## 検証項目

- ゲームのウィンドウ/フルスクリーンモードでキャプチャできるか。
- Ollama の Vision 対応モデルで画像入力が可能か。
- 画像サイズ、VRAM、推論時間。従来構想の10秒周期は例に留め、Phase 7 の確定値としない。
- 画面に個人情報や他アプリが映る場合の除外・停止方法。
- ゲーム規約やアンチチートとの適合性。ゲーム内部への介入や入力自動化は初期スコープ外。

## 初期技術スパイク

画面1枚をキャプチャし、Ollama に渡して説明文を得る実験は Phase 6 の開発検証として実施した。既存チャットの画像入力だけを根拠にせず、実 WGC と実 Vision の確認を上記に記録している。標準 Picker の実操作や継続監視の確認とは区別し、Phase 7 の詳細は Phase 6 の最終確認後に判断する。
