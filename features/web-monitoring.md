# Web 情報収集

**Phase 4:** 複数 RSS / Atom 情報源と自動巡回はユーザーセッションの独立 Worker に実装済み。現在の設定・復旧・制約は [Worker の実装・運用](background-worker.md) を参照する。以下の Phase 3 の記述は導入時の範囲を示す。

Phase 4 後の追加改修で、初回取得日による通知のグループ化、既読・未読、ブックマーク、手動タグ、ナビゲーション下部の Worker／AI 操作を実装した。[通知管理の実装状況](notification-management-implementation-status.md) に操作・検索範囲・移行・API を記録する。「すべて・タグなし」は全体最新100件内の情報源絞込を維持し、未読／ブックマーク／タグは DB 全通知へ条件を適用した最新100件を取得する。未読件数は全表示対象通知から集計する。

## 目的

通知一覧からの ☆／★ と単体削除、削除確認の設定、メタデータ末尾の未読表示は [クイック操作の実装状況](notification-quick-actions-implementation-status.md) を参照する。DB・Worker API・検索範囲は変更せず、単体削除は既存の記事削除サービスを使う。

興味のあるニュース、ソフトウェアのリリースノート、Factorio MOD 更新情報を自動・手動で収集し、変更点を AI が要約して Markdown と通知フィードに残す。

## 情報源

- RSS / Atom（実装済み）: ニュース、技術ブログ。Phase 5 でも既存の収集機能を維持する。
- GitHub Releases（Phase 5 の合意範囲・未実装）: 最初の API 型情報源として、リポジトリ単位で監視対象を管理し、リリース ID 等で重複・差分を判定する。
- 一般 Web ページ（時期未定）: RSS / Atom や専用 API がない指定ページを対象に、HTML 取得・対象領域抽出・ハッシュ等で変更を検出する汎用 Web 監視を検討する。
- Factorio MOD Portal 等の固有 API（時期未定）: MOD のバージョン・互換性・更新内容。GitHub Releases より優先度を下げた後続候補として残す。

Phase 5 は情報源ごとに異なる取得・差分判定を整理し、既存 Worker の定期巡回・手動実行と Ollama 要約・通知・記事管理へ接続する。同じリリースを繰り返し取得しても無条件に新規通知を生成しないことを完了条件とする。既存の未読・既読、ブックマーク、手動タグ、削除と整合させる。

情報源ごとの ID、更新日時、ETag、Last-Modified、ハッシュなど利用可能な手段を検討する。`IContentSource` は契約名の例であり確定 API ではない。具体的な共通化は RSS / Atom と GitHub Releases に必要な範囲とし、汎用プラグイン基盤・MCP / Tool Calling・AI 管理コンソールを Phase 5 の必須要件にしない。認証・取得範囲・同一リリースの更新時の扱いなどは [未決定事項](../open-questions.md#phase-5-の詳細設計で確認) に残す。

## 関心テーマからの情報発見・推薦（将来構想）

登録済み URL の巡回とは別に、C# / .NET、AI モデル・AI エージェント、VS Code / Visual Studio / GitHub の新機能、開発ツール・セキュリティ等の関心テーマから、記事の検索・候補抽出・関連度評価・重複整理・要約・重要度別通知を検討する。処理負荷を抑える方向として、キーワードやメタデータによる一次選別とローカル LLM による二次評価の組み合わせも候補とする。

検索・推薦や AI による情報源の自動発見は Phase 5 に含めない。AI 管理コンソールは既存操作を自然言語で呼び出す入口であり、この情報発見・推薦処理自体とは分ける。詳細仕様・実装方式・順序・フェーズ番号は未定とし、[ロードマップの後続候補](../roadmap.md) として扱う。

## パイプライン

```text
スケジュール / 手動実行
  -> 取得 -> 正規化 -> 重複・変更検出
  -> 変更内容の保存 -> LLM 要約・分類
  -> 構造化結果の検証 -> Markdown 出力
  -> 通知保存 -> UI への配信
```

## 設定

情報源名、URL/識別子、取得方式、カテゴリ、巡回周期、ON/OFF、最終成功日時、実行状態などを管理する。1時間間隔は例であり、情報源ごとに設定可能とする。手動実行と自動実行は同じユースケースを呼ぶ。

将来の [AI 管理コンソール構想](ai-management-console-concept.md) でも、通常 UI と同じ Application Service の操作を利用する候補としている。先に通常の設定・実行を成立させ、自然言語からの操作やツール基盤は MVP に含めない。構想上の「監視テーマ」と情報源設定の対応は未決定であり、現時点の設定仕様へ追加しない。

## 巡回時の注意

- 毎回全文を LLM に渡さず、追加・変更された項目を優先する。
- API レート制限、タイムアウト、リトライ、条件付き GET を考慮する。
- 重複ニュースを異なる情報源から収集した場合の統合は後続課題。
- 重要度・破壊的変更は LLM の参考判定と明示的なリリース情報を分ける。
- 取得失敗と「新着なし」を区別して記録する。
- 原文・引用の保存と公開は権利や利用規約を考慮する。

## MVP

Phase 3 は RSS / Atom 1件の手動取得、SQLite による重複検出、Ollama 要約、Markdown 保存、巡回履歴・通知フィードまでを Desktop 内に実装する。スケジュール・Windows Service・複数情報源は Phase 4 以降とする。

実装済みの動作・再試行・安全性・制約・確認方法は [Phase 3 実装状況](web-monitoring-implementation-status.md) を参照する。上の情報源拡張・周期・分類・構造化結果は将来計画を含み、すべてが今回の実装対象ではない。
