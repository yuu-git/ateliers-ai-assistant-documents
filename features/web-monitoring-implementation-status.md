# Phase 3: Web 情報収集 MVP

この文書は Phase 3 導入時の記録。Phase 4 で通常起動の Web 処理を独立 Worker に移し、複数情報源・自動巡回・永続待機処理を追加した。現在の動作は [Worker の実装・運用](background-worker.md) を参照する。

通知 UI の現在の並び順は初回取得日時の降順。既読・ブックマーク・タグの永続化、条件適用後100件の検索、全通知の未読集計は [通知管理の実装状況](notification-management-implementation-status.md) を参照する。以下の公開日時順・操作配置は Phase 3 当時の記録とする。

確認日: 2026-10-29。既存4プロジェクト内へ追加し、新規プロジェクト・NuGet 依存は追加していない。

## 操作

現在の UI では [通知一覧のクイック操作](notification-quick-actions-implementation-status.md) も利用できる。単体削除の確認省略は Roaming 設定へ保存し、一括削除の確認には適用しない。以下の操作手順は導入時の記録。

1. 「Web 情報収集」を開き、公開 HTTP(S) の RSS / Atom URL を1件入力する。
2. 要約モデルを選択する。チャットの選択とは独立し、選択だけではロードしない。
3. 「取得」で設定を保存して収集を実行する。「設定を保存」だけなら取得しない。
4. 完了後、巡回履歴と通知フィードを確認する。同じ URL で再実行しても完了済み記事を再通知しない。
5. 通知を選ぶと一覧下部に本文の全文を Markdown 表示する。「元記事を開く」または「保存 Markdown を開く」でも参照できる。
6. 「記事をまとめて削除」で専用ダイアログを開き、1件または複数件を選択する。「すべて選択」「選択解除」と対象件数の表示があり、確認後に削除する。対象は現在表示中の最大100件で、さらに過去の記事があれば削除後の一覧へ表示される。

毎回、フィード内の記事を公開日時の新しい順で最大10件に絞って登録・要約する。日時不明の記事は既知日時の記事より後に置き、フィード内の順序を維持する。既存の通知を10件へ自動削除する意味ではなく、表示上限は引き続き100件とする。

### 記事単位・複数記事の削除

選択した記事の通知、入力・要約・重複判定キー、保存 Markdown を削除する。巡回実行履歴や未選択の記事、チャットの会話は削除しない。非表示機能は実装しない。

削除後、次回取得の最新10件に含まれる記事は新しい内部 ID で登録し直し、再要約・保存・通知する。配信元が既に記事を掲載していない場合や最新10件の範囲外なら復活しない。削除確認にもこの条件を表示する。

削除は収集と同じ Application Service の排他権で調整し、DB・ファイルの操作を ViewModel へ置かない。固定の内部 ID から Markdown のパスを作り、DB にある任意パスは削除しない。記事単位のトランザクションで通知をカスケード削除する。ファイル削除に失敗した記事は DB の削除をロールバックして残し、ほかの対象は継続する。欠損ファイルや削除済み ID は再削除できる。成功・失敗・中止を画面に表示する。

SQLite とファイルシステムをまたぐ完全な原子性は保証しない。ファイル削除後に DB 確定が失敗した場合はエラーを表示し、同じ記事を再度削除して回復する。削除中の強制終了も保証対象外とする。

画面を切り替えても収集は継続する。「中止」で中止できる。通常終了時は収集を中止し、履歴確定を最大8秒待ってから従来の期限付きモデル解放へ進む。強制終了時の確定・解放は保証しない。

起動時にモデル・URL・履歴・通知を復元するが、自動ロード・自動取得はしない。モデルがない場合は一覧更新・再選択を求める。設定保存に失敗した場合も今回だけの手動実行は可能で、エラーを表示する。不正 JSON を自動上書きしない。

チャットと通知のドメインモデルは統合しない。通知は共通 `NotificationDto` を包み、元 URL・成果物参照・記事の公開日時を追加する。一覧はタイトルと日時・URL を表示し、選択した通知の全文を下部の1つの WebView2 で Markdown 表示する。通知ごとに WebView2 を生成しない。Markdown 原文は維持し、既存の Markdig・HtmlSanitizer・ローカル highlight.js と外部遷移制限を共用する。見出し・太字・リスト・表・コードブロックと対応言語のシンタックスハイライトを表示する。

通知本文は選択時に先頭から表示し、長文も1,000文字で切り詰めない。表示の世代管理で古い非同期結果による上書きを防ぎ、初期化前の選択や選択解除も反映する。WebView2 が利用できない場合は原文表示へ切り替える。ViewModel は HTML 変換や WebView2 を扱わず、Desktop の表示用スナップショットを渡す。

通知一覧・本文プレビュー・削除選択の補足情報には「取得: RSS / Atom / 要約モデル: モデル名」を表示する。フィード取得はアプリの HTTP 処理であり、AI モデルは要約を担当する。`WebArticles.Model` の保存済みの値を `ArticleNotification.SummaryModel` へ渡し、現在の選択モデルや最後に巡回したモデルから推測しない。過去の記事・別モデルでの重複取得・アプリ再起動後も、実際にその記事を要約したモデル名を維持する。記録が欠ける場合は「不明（記録なし）」とする。DB Migration や再取得は不要である。

通知は記事の公開日時の降順とする。公開日時不明の記事は通知作成日時で代用し、画面にも「公開日時不明」と明記する。同一日時は通知作成日時の降順、さらに ID で順序を固定する。全通知をこの規則で並べた後に100件を選ぶ。既存 DB の記事入力 JSON に保持済みの公開日時を使うため、追加 Migration やフィードの再取得は不要である。従来の通知作成日時順では、フィードを先頭から要約した結果、古い記事ほど後で通知を作成され、上に来ることがあった。

追加改修の確認: 通知102件による公開日時優先・同日時・日時不明・並び替え後の100件選択を自動検証し、Debug / Release とも全48シナリオが成功した。実画面では通知全文の見出し・太字・リスト・表・C# 強調表示、長文の末尾、先頭からの表示、HTML の安全性、連続選択・選択解除を確認した。既存チャットの Markdown・ストリーミング・安全性・スクロールの実画面検証も成功している。

## 取得・入力の安全性と上限

- RSS 2.0 / Atom を `XmlReader` / `XDocument` で解析する。DTD・外部エンティティは禁止。
- 公開 HTTP(S) のみ。資格情報付き URL、ローカル名、非公開 IP を拒否する。接続時の DNS 結果を検査し、その IP へ直接接続する。リダイレクトは最大5回で各 URL を再検証する。Cookie・Proxy は使用しない。
- 取得は30秒、展開後2 MiB、解析は200記事まで。登録・要約の対象は、その中の最新10記事とする。本文は先頭12,000文字まで。空フィードは取得0件の成功として扱う。
- フィード提供の本文または概要のみを使用し、リンク先は取得しない。入力範囲と切詰めの有無をプロンプト・成果物へ明記する。
- 記事情報を信頼できない JSON データとして依頼する。データ中の指示に従わないよう固定指示を付け、ツール・内部操作を実行する経路を設けない。要約の正確性そのものは LLM に依存する。
- 要約は記事ごと3分、32,000文字まで。チャット履歴とは独立した1メッセージとして既存 Ollama ポートへ渡す。
- 元記事を開く際も URL を検証する。保存 Markdown は外部タイトルや DB の任意パスを実行せず、内部 GUID から固定パスを生成する。

## 重複と再試行

フィード URL はフラグメントを除きクエリを保持する。記事の一意キーはフィード URL と、GUID / Atom ID、記事 URL、タイトルと公開日時の順に選んだ識別情報の SHA-256 とする。記事 URL からはフラグメントと `utm_*` / `fbclid` / `gclid` だけを除去する。未知のクエリや順序は変えない。

`WebArticles.Key` は DB の一意制約で保護する。取得入力、成功済み要約とモデル、保存相対パス、通知確定、エラーを別々に保存する。

| 失敗段階 | 次回の処理 |
| --- | --- |
| 取得・モデル検証 | 実行履歴に失敗を残し、次回取得をやり直す |
| 要約 | 保存済みの入力から要約を再試行 |
| Markdown 保存 | 成功済み要約を再利用して書込を再試行 |
| ファイル保存後・通知確定前 | 同じファイル名へ再出力し、通知を冪等に確定 |
| 中止・強制終了 | 未完了記事は再試行。終了未確定の履歴は未完了と表示 |

再試行は同じフィード URL の次回取得が成功した際に行い、今回の最新10件に含まれる DB の未完了記事を対象にする。範囲外の未完了記事は保持するが、その回には再試行しない。完了済み記事は、明示削除しない限り更新による再要約・再通知を行わない。

Markdown は `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\web-monitoring\articles\{内部GUID:N}.md` に保存し、Debug は `Ai-Assistant.Debug` を使う。タイトル・元 URL・公開日時・取得日時・モデル・入力範囲・要約を UTF-8 で出力し、同一ディレクトリの一時ファイルから置き換える。ファイル保存後、保存パスと通知を DB の1トランザクションで確定する。`WebNotifications.ArticleId` は主キー兼外部キーであり、記事1件につき最大1通知となる。

## モデル・履歴・保存

収集全体を `ChatModelSession` の排他区間に置き、記事間も含めチャット送信・モデル変更・停止との競合を拒否する。`/api/ps` は引き続き全体の観測だけに使い、収集で使用したモデルも内部で追跡する。管理対象モデルだけを通常終了時に解放し、Ollama サーバーは停止しない。複数機能を並行実行する参照数管理は今回導入していない。

実行履歴は開始・終了・情報源・モデル・状態、取得／新規／重複／今回の要約成功／記事失敗の件数、エラー概要を保持する。ファイルのみ再試行した場合、今回の要約成功件数は増えない。巡回履歴・通知の画面は最新100件を表示し、DB の過去データは自動削除しない。

Migration `20261028204923_WebMonitoring` は既存会話テーブルを変えず、Web 3テーブルを追加する。会話と Web は同じ DB ゲートを共有し、アクセスと Migration を直列化する。破損・消失時に DB を削除して作り直す処理は追加しない。

## 対象外・制約

定期実行、Windows Service、複数フィード管理、全文ページ抽出、ブラウザー操作、MCP、AI 管理コンソール、OS トースト、分類・重要度の構造化結果、検索・同期は実装しない。

RSS 1.0、独自拡張、XML Base、外部 content の取得等の全仕様は網羅しない。URL 変更時に同じフィードと判定する機能、更新記事の自動再通知、複数プロセス間の収集調停、通知の既読、実行履歴の削除や保持期間は今後の課題。代替キーのみの記事はタイトル・公開日時が変わると別記事になり得る。Proxy 必須環境・ローカルフィードは今回対応しない。同じモデルを他アプリも使用する場合の停止影響は従来どおり運用で調整する。
