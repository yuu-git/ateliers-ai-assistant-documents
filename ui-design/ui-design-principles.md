# UI 設計原則

## 目的

機能追加に伴い、設定・履歴・通知・実行操作が同じ画面に積み上がっている。プロトタイプ段階でも **「今どこにいるか」「何を確認する画面か」「次に何を操作するか」** を明確にする。

## 基本原則

1. **機能と管理を分ける。** 利用者の目的（通知を見る・チャットする）と、保守目的（設定・ログ・モデル管理）をナビゲーションで区別する。
2. **1画面に主目的を1つ置く。** Web 情報収集の主目的は通知・記事の閲覧。情報源設定、巡回履歴、削除は副操作へ移す。
3. **頻度の高い操作を優先する。** 通知閲覧、チャンネル切替、記事詳細、手動巡回を見つけやすくする。
4. **破壊的操作を目立たせすぎない。** 一括削除・停止などは明示的なメニュー/管理領域に置き、確認を残す。
5. **状態を明示する。** Worker の接続、AI 一時停止、巡回中/失敗/待機、空データを区別する。
6. **横幅を活かす。** 横長画面ではリスト・詳細を並べるが、本文の行長は制限し読みやすくする。空白を単純に埋めるための装飾はしない。
7. **既存のダーク配色を暫定維持。** 色の全面改定や独自テーマ作成はしない。コントラストとフォーカス可視性は確保する。
8. **WinUI 3 / XAML / MVVM を継続。** 参考画像が Web UI に見えても Blazor/WebView2 への置換を要求しない。チャットの既存 WebView2 は維持する。
9. **UI は実行責務を持たない。** Worker API、Application Service、設定、SQLite の既存境界を保つ。
10. **実画面で検証する。** ビルド成功だけでなく、代表サイズ・DPI・スクロール・キーボード操作を確認する。

## 共通のレイアウト規則

- アプリの左側にトップレベルナビゲーション。見出し付きの「機能」「システム・管理」に分類する。
- 各ページは見出し、必要なら短い説明、主要操作、コンテンツの順。
- 設定は最大幅を持つコンテンツ列にカード/セクションとして表示し、長い説明文を画面全幅に伸ばさない。
- 過密なボタン列、意味のない同種の見出し重複、細かすぎる常時表示メタデータを避ける。
- ステータスは色だけに頼らず、テキスト・アイコンでも表現する。
- 日本語の文言を統一（例：情報源／巡回／要約待ち／通知／ログ）。

## 禁止・非目標

- Phase 1～4 の既存機能の削除や動作変更を UI 改修の名目で行わない。
- 画面を綺麗にするために DB スキーマや Worker の契約を独断で変更しない。
- デザイン画像の見た目をピクセル単位で複製することを要求しない。
- 架空の AI ニュースやチャンネルを初期データとして追加しない。モック画像の文字は例示。
- 未実装の通知カテゴリ・RSS 登録・高度なフィルターを実装済みと見せかけない。
