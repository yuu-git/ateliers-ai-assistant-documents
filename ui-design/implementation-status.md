# Phase 4 後の UI 整理・実装状況

2026-10-29。WinUI 3 / XAML / MVVM を維持し、ナビゲーション、通知・情報収集、設定を整理した。承認された例外として通知応答に取得元フィード URL を追加した。収集・要約・保存の方式を再設計する変更は行わない。

同日、追加指示に基づく [通知管理・グローバル操作](../features/notification-management-implementation-status.md) を実装した。以下の配置・表示範囲はこの追加改修を含む。末尾の64シナリオは初回 UI 整理時点の検証記録であり、追加改修の移行・API・最新の検証結果はリンク先を参照する。

## 機能の配置

通知一覧の操作は [クイック操作の追加調整](../features/notification-quick-actions-implementation-status.md) により、独立した ☆／★ とゴミ箱、単体削除確認と設定、補助情報行末尾の未読表示へ変更した。既存の一括削除、Worker、表示条件・API・DB スキーマは維持する。

| 目的 | 操作場所 |
| --- | --- |
| 通知を見る | 「機能」→「通知・情報収集」。初期表示は通知一覧 |
| 情報源別に見る | 「すべての通知」または現在登録されている情報源を選ぶ |
| 記事を読む | 一覧から選択。横長は右ペイン、狭幅は詳細表示と「通知一覧へ戻る」 |
| 巡回履歴を見る | 通知／巡回履歴の切替。新規0件の結果も履歴で確認 |
| 手動巡回する | 個別の情報源を選択→「手動巡回」。「すべて」は閲覧用 |
| 情報源を追加・編集する | 「情報源設定」ダイアログ。名称・URL・周期・自動取得を保存 |
| 情報源を削除する | 同ダイアログ内で対象を選択→削除→同じ画面内で確認 |
| 記事を一括削除する | 「管理」→「表示対象の記事をまとめて削除」。選択・全選択・解除・確認を維持 |
| Worker を操作する | ナビゲーション下部または設定の Worker カード。設定再読込・起動登録は設定画面 |
| 接続を復旧する | 通知画面の「接続の詳細・復旧」から開始または設定へ移動 |
| AI を一時停止する | 固定フッターまたは設定の即時操作。他の編集中設定を保存せず RSS は継続。従来のチェック編集→保存も維持 |
| モデル方針を変える | 同カードで要約モデル・自動ロード／アンロードを編集して保存 |
| 保存先を確認する | 設定のデータと保存先カード。選択・コピー可能な固定パスと各フォルダー起動 |
| チャット・モデル・ログを使う | 既存画面と機能を維持。ログの操作列は狭幅で折り返す |

アプリ起動時の初期画面は従来どおり AI チャット。トップレベルの `Chat` / `Models` / `Web` / `Logs` / `Settings` を維持し、チャット離脱時の保存確認も変更しない。

## 表示範囲と情報源の意味

- `ArticleNotification.SourceUrl`: 元記事 URL。元記事を開く操作に使う。
- `ArticleNotification.FeedSourceUrl`: 取得元フィード URL。既存 DB の `WebArticles.Source` から応答へ含める。DB Migration、取得・要約処理、保存済み記事の書き換えは不要。
- 「すべて・タグなし」は **全情報源の最新100件** に情報源を適用する。未読／ブックマーク／タグ指定は DB 全表示対象通知へ条件を適用した最新100件。並び順は初回取得日時の降順で、ページングはない。未読集計は100件制限に依存しない。
- 削除済み情報源は選択肢へ出さない。通知自体は「すべて」で引き続き表示し、登録名がない場合はその旨を表示する。元記事 URL のホストから情報源を推測しない。
- 一括削除は現在の表示対象（最大100件）を確認ダイアログへ渡す。「すべて」なら従来の全体最新100件が対象。巡回履歴を残し、取得の最新10件に含まれれば新規再取得できる仕様も維持する。
- Worker の取得結果と AI 要約は独立した段階として表示する。取得履歴の件数を AI 処理全体の進捗と見なさない。

取得元 DTO の追加時は実装版 `4.0.1`、通知管理 API の追加後は **`4.1.0`**。旧 Worker が起動している場合は、**旧アプリの設定画面から Worker を停止し、更新後のアプリで開始し直す**。UI と Worker の版が不一致の場合に無条件で接続する挙動は追加しない。

旧アプリを利用できない場合は、タスクマネージャーで実行ファイルの場所を確認し、対象環境の自分の `Ateliers.Ai.Assistant.Worker` を終了してから開始し直す。Ollama サーバーの終了は不要。

## 更新・編集中の状態

登録情報源・通知の同じ行は再利用し、差分の挿入・移動・更新だけを反映する。閲覧中の情報源と、情報源設定の編集対象は別の状態にする。取得後に同じ記事を選び直したり、変更のない Markdown を再表示したりしない。

- 約5秒の既存ポーリングを再利用し、UI 改修を理由にポーリングを増やさない。
- 状態更新と結果の再取得で、記事選択・情報源選択・Markdown のスクロール位置を維持する。
- 閲覧中は記事選択を保持する。2026-10-30 の修正で、狭幅の戻る・履歴／画面／条件切替は閲覧終了として詳細を閉じ、明示的に開いた記事だけ既読にする。手動で未読に戻した場合は維持する。明示的な既読変更・ブックマーク解除で一覧から外れた記事の詳細は保持する。[現在の閲覧仕様](../features/notification-reading-behavior.md) を参照する。
- 通信失敗時もキャッシュ済みの記事と選択を消さず、接続状態を別に示す。
- 初回接続前の入力も含め、定期更新で AI・情報源の編集値を上書きしない。
- 情報源の保存で AI の未保存入力を破棄せず、AI 保存で情報源の未保存入力を保存・破棄しない。
- 保存を待つ間に続けて入力した変更も維持し、古い保存の完了で新しい入力を上書きしない。
- Worker 設定の明示再読込は、未保存変更がある場合に確認する。保存失敗時は入力を残す。
- 設定の保存単位と、起動登録が操作時に即時反映することを画面で説明する。

## レイアウトと参考画像との差

通知ビュー自体の幅が1200以上なら3ペイン、820以上1200未満なら情報源を選択メニューにして2ペイン、820未満なら一覧／詳細を切り替える。トップナビゲーションも幅に応じて折りたたむ。全ウィンドウ幅とビュー幅は異なるため、数値はウィンドウ幅の固定仕様ではない。

- 元画像の情報階層と通知中心の構成を採用する。Blazor へ移行せず、架空のチャンネル・ニュース・重要度・巡回完了通知は追加しない。
- モック画像のタブは標準の選択コントロールによる通知／履歴切替とした。独自の外部 UI ライブラリは追加しない。
- Worker の概要と復旧は通知画面内にも残し、追加改修で共通ナビゲーション下部に実状態・AI 即時操作を追加した。狭幅は短縮表示と展開操作を使う。フィルターと記事操作も展開領域へまとめ、本文を読む幅・高さを確保する。
- 設定は最大幅900のカード列と縦スクロールを使う。モック画像の右側の「画面設計のポイント」は製品機能ではないため表示しない。
- 情報源管理と削除はダイアログ／メニューへ移し、通知一覧の常設フォームをなくした。長い説明・注意文は省略せず設定側へ残す。
- 配色は既存テーマと WinUI のリソースを使用し、参考画像の寸法・色を厳密に複製しない。

## 確認方法

```powershell
dotnet build src/Ateliers.Ai.Assistant.Desktop -p:Platform=x64 -p:WindowsPackageType=None -p:WindowsAppSDKSelfContained=false
dotnet build src/Ateliers.Ai.Assistant.Desktop -c Release -p:Platform=x64 -p:WindowsPackageType=None -p:WindowsAppSDKSelfContained=false
dotnet run --project tests/Ateliers.Ai.Assistant.Desktop.Tests
dotnet run --project tests/Ateliers.Ai.Assistant.Desktop.Tests -c Release
powershell -File tests/Verify-UiRefactoring.ps1
```

各段階で Debug ビルド・既存テストを実施し、Debug / Release 各64シナリオの成功を確認した。追加テストは、同一の記事 URL を持つ異なるフィードの識別、削除済み情報源、表示対象だけの一括削除、行の同一性、初回接続前を含む入力保持、保存単位、再読込の確認、保存失敗、保存待ち中の新しい編集を扱う。

実画面では、記事・情報源の選択、Markdown の安全化と C# ハイライト、ポーリング前後の実スクロール値、履歴切替、幅変更と戻る、AI の実入力バインド、一括削除ダイアログの選択・確認、既存ナビゲーション、Worker 切断時のキャッシュ保持を確認した。取得元と記事 URL の分離は、実 SQLite からの復元と、独立 Worker の HTTP 応答でも確認した。

既存の回帰確認も成功:

| スクリプト | 結果 |
| --- | --- |
| `Verify-WorkerProcess.ps1` | 認証・起動排他・AI 方針・強制終了復旧・API の取得元 URL 分離・削除後再取得 |
| `Verify-WorkerDisplay.ps1` | 実情報源入力、次回予定、AI 停止、UI 終了後の巡回、オフラインのログ・チャット |
| `Verify-MarkdownDisplay.ps1` | 書式・安全化・ストリーミング・中止／失敗・スクロール・過去の描画結果の拒否 |
| `Verify-StorageDisplay.ps1` | 会話・画像・下書き・未保存確認・別プロセス復元・追記・削除 |
| `Verify-WebMonitoringDisplay.ps1` | 既存の手動ホスト、通知全文、C# ハイライト、再起動復元 |
| `Verify-WebArticleDeletion.ps1` | 実ダイアログの複数選択・確認取消・全選択／解除・削除・新規再取得 |

従来の UTF-8（BOM なし）スクリプトは PowerShell 7 (`pwsh`) で実行した。新しい `Verify-UiRefactoring.ps1` は Windows PowerShell でも読める UTF-8 BOM 付きとする。

実画面検証は偽 Worker / モデルと一意の一時保存先で実施する。スクリーンショットはアプリ側 `artifacts/ui-refactoring/` に出力し、通常のデータや実モデルに依存しない。DOM による Markdown・C# ハイライトの検証に加え、黒い空画面を画像として合格させないチェックも行う。保存先画面には一時パスを含むため、画像は公開用文書へ自動追加しない。

確認サイズは1600×1040、1150×950、760×950、480×800、実環境の表示倍率100%。別 DPI・複数モニターでの最終操作感は手動確認が残る。キーボードでは各選択、Tab 移動、狭幅時のナビ展開と戻る、ダイアログ・スクロールを利用者環境でも確認する。

OS のサインイン起動・スリープ復帰、実 Ollama の応答品質は今回の UI 検証の対象外。Worker の起動方式・Ollama 方針・DB スキーマ・保存先・チャットの保存や画像入力・ログの保存方式は維持する。ビルドでは既知の `NU1900`（NuGet の脆弱性情報へ接続不可）が残る。
