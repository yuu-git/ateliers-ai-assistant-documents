# Codex 実装指示 — 通知一覧の操作性改善（単体削除・未読・ブックマーク）

## 目的と範囲

Ateliers AI Assistant の既存 WinUI 3「通知・情報収集」画面について、機能追加を最小限に抑えつつ、通知一覧からの日常操作を簡単にする。現在の Worker、RSS 収集、AI 要約、記事詳細、タグ、巡回履歴、データ保存、既存一括削除機能は維持する。全面的な UI 再設計や新たなナビゲーション基盤の導入は行わない。

まず現行 XAML、ViewModel、Application Service、SQLite/EF Core の記事・通知削除処理、設定保存処理、既存テストを調査し、再利用できる実装を特定すること。必要な契約・DB 変更がある場合は影響を報告する。以下の仕様を満たす範囲で実装し、Debug/Release ビルドと回帰テストを実施すること。

## 1. 通知一覧の操作ボタン

- 各記事の現在の「☆保存」ボタンを、アイコンのみの「☆」ボタンへ変更する。未保存／保存済みが視覚的に識別できるようにする（塗りつぶし等）。既存の `IsBookmarked` の永続化・絞り込みを維持する。
- アイコンボタンにはツールチップ、アクセシブル名（例：「ブックマークに追加」「ブックマークを解除」）、キーボード操作、適切なクリック領域を用意する。文字がないことによって操作の意味が不明瞭にならないようにする。
- 「☆」の直下（各記事行の同じ操作列）にゴミ箱アイコンの「記事を削除」ボタンを追加する。行選択や既読化とは独立して操作できること。
- 削除成功後は現在の一覧・未読件数・情報源別件数・ブックマーク一覧・タグ絞り込み・詳細選択を矛盾なく更新する。選択中の記事を削除した場合、詳細表示を適切にクリアする。削除失敗時は成功扱いにせず、原因をユーザーに表示する。
- 削除処理は既存の単体記事削除／一括削除と同じ Application Service 等を再利用する。UI から直接 DB や Markdown ファイルを操作しない。既存仕様どおり通知・要約・Markdown・重複判定情報を削除し、巡回履歴は残す。次回フィードに存在すれば新規として再取得可能とする。

## 2. 単体削除の確認と設定

- 既定では単体記事削除の前に確認ダイアログを表示する。記事タイトルを示し、「この記事を削除しますか？」と、通知・要約・保存 Markdown 等が削除され、再取得時は新規扱いになる旨を簡潔に説明する。
- ダイアログには「次回以降は確認しない」チェックボックスを設ける。チェックして**削除を確定した場合のみ**、以後の単体削除確認を無効にする。キャンセル／閉じる／失敗時には設定を変更しない（削除が成功した場合に設定を確定する）。
- この設定はアプリの既存ユーザー設定保存先・環境分離（Debug/Release）に従って永続化する。設定画面には「記事の単体削除前に確認する」の ON/OFF を追加し、いつでも再有効化できるようにする。初期値は ON（確認する）。既存設定の互換性を保つ。
- 確認を省略していても、一括削除の確認ダイアログには影響を与えない。単体削除と一括削除は設定を共有しない。
- 削除ボタンの連打・多重実行、非同期処理中の再操作を防ぐ。設定保存と削除の順序、キャンセル時の副作用をテストする。

## 3. 未読表示の位置と文言

- 通知一覧の独立した「既読」ラベルは廃止する。既読記事には状態ラベルを表示しない。
- 未読記事だけ、各記事の最下段の補助情報行（例：「VS Code ・ 初回取得 2026/...」）の**末尾**に「未読」を表示する。赤系のアクセント色で目立たせる。ただしテーマ変更時の可読性・コントラストを確保し、色だけに依存せず文字も表示する。
- 既読・未読の切替で行高やタイトル・概要・メタデータの位置が不自然にずれないよう、同じ補助情報行内で表示を切り替える。必要に応じて表示領域を確保するが、不必要な空白は増やさない。
- 既存の既読化タイミング、`ReadAt` 永続化、手動で未読へ戻す機能は維持する。

## 4. 未読のみ／ブックマークのみの一覧

- 通知画面の表示条件に「すべて」「未読のみ」「ブックマークのみ」を設ける。既存のタグ指定・情報源選択との関係が分かるようにし、選択状態を UI に明示する。
- **すべて（タグ指定なし）**：既存仕様どおり、全体の最新100件を取得してから情報源で絞り込む。
- **未読のみ／ブックマークのみ／タグ指定あり**：DB の全通知へ条件を適用してから、初回取得日時の降順で最新100件を取得する。情報源絞り込みも、既存の合意仕様との整合を確認して適用する。古い未読・保存記事が「全体の最新100件」に含まれないという理由だけで見えなくならないこと。
- 未読件数バッジは DB の全通知を対象とする既存の仕様を維持する。表示件数と未読総数を混同しない。
- 未読のみ表示中に記事を既読にした場合や、ブックマークのみ表示中に解除した場合、対象が一覧から消える挙動を自然に扱う。操作後の選択・スクロール位置が不必要にリセットされないようにする。
- 空状態（該当なし）を分かりやすく表示する。定期更新時に現在の表示条件を維持する。

## 5. UI・設計上の制約

- 既存のナビゲーション、日付グループ、情報源選択、記事詳細の WebView2、タグ編集、Worker 操作、設定画面のカード構成を維持する。
- ゴミ箱・ブックマーク操作はマウス・キーボード双方で利用可能にする。必要に応じてツールチップを付ける。
- 既存のアプリケーション設定契約とデータ保存ポリシーに従う。今回の要件のために不要な新規 DB カラムを追加しない。削除確認設定の保存先は既存のユーザー設定に統合する。
- 設定の変更や削除結果は適切にログへ記録する。ただし個人情報や記事本文を過剰にログへ出力しない。
- 既存の設計資料（`ateliers-ai-assistant-documents/ui-design/`、`features/web-monitoring*.md`、必要に応じて `data-design.md`）へ、確定した仕様・画面操作を反映する。

## 6. 検証・完了条件

1. ☆のみでブックマークの追加／解除ができ、再起動後も保持される。
2. 各通知のゴミ箱から単体削除できる。既定では確認が表示され、キャンセルでは一切削除されない。
3. 「次回以降は確認しない」を選んで削除成功後、次の単体削除は確認なしで実行される。設定画面から再度 ON にできる。一括削除は常に従来の確認を維持する。
4. 未読のみ赤色の「未読」がメタデータ行末尾に表示され、既読には表示されない。状態変更でレイアウトが不自然に動かない。
5. すべて／未読のみ／ブックマークのみを切り替えられ、DB 全体からの取得条件、100件上限、情報源・タグ指定が合意仕様どおり動作する。
6. 削除後の件数・一覧・記事詳細・Markdown・重複判定に不整合がなく、再取得可能性と巡回履歴保持も既存仕様どおり。
7. Debug/Release ビルド、既存テストと追加テストが成功し、狭幅を含む実画面で操作を確認する。

完了時には、変更ファイル、変更した設定／契約、検証結果、残課題を報告すること。既存実装の構造上、仕様を満たすために大幅な変更が必要な場合は、独断で拡張せず先に相談すること。
