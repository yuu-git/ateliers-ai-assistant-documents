# Phase 5 — 情報源拡張基盤・GitHub Releases 対応：Codex 実装指示

## 0. 依頼の目的

Ateliers AI Assistant の Phase 5 を実装してください。既存の RSS / Atom 収集を維持しながら、最初の API 型情報源として **GitHub Releases** を追加します。取得方法が異なっても、既存の Worker による巡回、重複・差分判定、Ollama 要約、通知、記事管理を共通利用することが目的です。

**まず現行コードと設計資料を調査し、変更計画と仕様上の確認事項を提示してください。調査・計画の承認前に実装を開始しないでください。** 特に DB Migration、API 契約、Worker の実行方式、既存通知 ID の取り扱いは独断で確定しないこと。

- `ateliers-ai-assistant-documents/roadmap.md`（更新済み Phase 5 の定義）
- `requirements.md`、`architecture.md`、`data-design.md`、`data-storage-policy.md`（存在する場合）、`development-guidelines.md`、`open-questions.md`

実ファイル名・実際の構造を優先してください。文書とコードが食い違う場合は差分を報告してください。Phase 3・4 と UI 改修で確立した既存の挙動を壊さないでください。

## 2. 実装範囲

1. **情報源の種別**：RSS / Atom と GitHub Releases を識別し、既存の情報源管理画面から登録・編集・有効無効・削除・手動実行・周期設定を扱えるようにする。GitHub は `owner/repository` 単位を基本とする。入力値を正規化・検証し、表示名と取得先を区別する。
2. **取得基盤**：既存の RSS 収集実装を極力再利用しつつ、情報源種別に応じた取得処理を分離する。過剰なプラグイン機構や MCP は導入しない。取得結果は共通の保存・要約・通知パイプラインへ渡す。
3. **GitHub Releases**：公式 GitHub REST API のリリース一覧を取得する。初期対象は公開リポジトリとし、API の JSON を適切に解析する。リリースのタイトル、本文、URL、公開日時、タグ名、リリース ID、draft/prerelease 情報を取得可能な範囲で扱う。HTML ページのスクレイピングを基本方式にしない。
4. **重複判定**：GitHub Release ID を情報源内の安定識別子として利用する。リポジトリの同一性も考慮する。再巡回で既存リリースを無条件に再通知・再要約しない。RSS の既存重複判定は維持する。
5. **要約と通知**：取得した Release 本文等を既存 Ollama 要約処理へ連携し、現在の通知一覧・詳細・未読・ブックマーク・タグ・削除操作で扱えるようにする。情報源フィルタと未読件数も正しく更新する。
6. **Worker**：既存のユーザーセッション常駐 Worker、手動実行、定期巡回、AI 一時停止、モデル自動ロード／アンロードの許可設定、失敗時の再試行・復旧方針を踏襲する。UI を閉じても動作すること。
7. **ログと状態**：取得成功・新規件数・重複件数・失敗・レート制限等を既存の巡回履歴・アプリケーションログ・システムログへ適切に記録する。機密情報はログに残さない。

## 3. 仕様上の初期提案（調査後に確認すること）

- **対象**：まず公開 GitHub リポジトリのみ。プライベートリポジトリや GitHub Enterprise、ユーザー認証 UI は今回対象外。
- **認証**：初期は認証なしで動作する最小構成を検討する。ただしレート制限が厳しいため、既存の安全な秘密情報管理基盤があれば任意トークン対応の是非を提案する。新しいトークン保存方式を独断で導入しない。
- **リリース対象**：公開済みの正式リリースを既定とし、draft は除外、prerelease の収集可否は情報源単位の設定候補として提案する。既定値と UI への影響を調査後に確認する。
- **初回取得**：既存 RSS の「最新10件」方針との整合を確認する。GitHub Releases も初回の取得・登録対象件数に上限を設け、過去リリースの大量通知を防ぐ。件数・ページング・以降の巡回範囲は実装前に提案する。
- **リリース編集**：同じ Release ID の本文やタグが編集された場合に「既存記事を更新する／無視する／再通知する」のどれを採用するか、既存の重複判定との整合を踏まえて提案する。無条件の再通知は避ける。
- **公開日時**：GitHub 側の `published_at` とアプリ内の初回取得日時を混同しない。既存の「初回取得日時で日付グループ化」を維持する。
- **削除・再取得**：既存仕様と同様、記事を削除した場合は重複記録も消え、次回の取得対象に含まれれば新規として再登録できるようにする。巡回履歴は残す。
- **RSS と API の同一内容**：別情報源間の高度な横断重複統合は必須にしない。衝突や識別子の名前空間に注意する。
- **HTTP**：`HttpClient` の既存 DI・タイムアウト・キャンセル・User-Agent・レスポンスサイズ制限等の方針を確認。`403`/`429` とレート制限関連ヘッダー、`404`、`5xx`、ネットワーク断、JSON 解析失敗を適切に扱う。失敗を「更新なし」と誤表示しない。可能なら ETag / 条件付きリクエストを検討するが、過剰実装は避ける。

上記は未確定事項を含むため、実装前の計画提示時に、推奨値とその理由を明記してください。

## 4. アーキテクチャ上の要件

- Application 層は GitHub 固有 HTTP 実装に直接依存しない。HTTP/JSON 取得は Infrastructure 等の適切な層に置く。
- 既存の Worker と UI の通信経路を維持する。Desktop から直接 API を巡回して、UI 終了後に停止する構成にしない。
- RSS の既存 DB と履歴を保持する。必要な Migration は既存データを保全し、Debug / Release のデータ保存先分離を維持する。
- 共通 DTO・識別子・差分判定の責務を明確化する。`SourceUrl`（元記事 URL）と取得元情報源の区別を維持する。
- 将来の API 型情報源を追加できる程度の拡張性を持たせるが、未実装の一般 Web / Factorio 向け抽象化を先回りして作り込まない。
- 認証トークンを追加する場合は Roaming/Local の保存方針、平文保存回避、ログへの漏えい防止を事前確認する。

## 5. UI 要件

- 既存の「通知・情報収集」の情報源管理から RSS / Atom と GitHub Releases を選択して登録できること。
- 種別に応じて入力項目とバリデーションを変える。GitHub は `owner/repository` が基本。入力例やエラー理由を分かりやすく表示する。
- 既存の情報源別ナビゲーション、通知一覧、詳細、未読件数、ブックマーク、タグ、記事削除を再利用する。
- 既存の UI 設計指針に従い、情報源追加に伴う新しいメイン画面や複雑な設定画面を増やさない。
- アクセス制限・レート制限・存在しないリポジトリ等の失敗理由をユーザーが確認できること。

## 6. テストと完了条件

最低限、次を検証してください。

1. 既存 RSS / Atom の手動巡回・定期巡回・重複検出・通知・削除後の再取得が回帰しない。
2. 公開 GitHub リポジトリを登録し、リリースを取得して要約・通知できる。
3. 同じリリースを2回取得しても無条件に再通知されない。
4. 別リポジトリの同名タグ／リリースでも誤って同一扱いしない。
5. 初回取得件数上限、正式版／プレリリース、draft、編集済みリリースの方針どおりに動く。
6. API 障害、レート制限、404、タイムアウト、キャンセル、Ollama 停止、AI 一時停止から安全に復旧する。
7. Worker の UI 非依存、再起動後の設定復元、Debug / Release 分離を維持する。
8. GitHub 通知で未読・ブックマーク・タグ・削除・情報源絞り込み・巡回履歴が正しく機能する。
9. HTTP 通信は可能な限りモック／スタブで再現可能な自動テストを用意し、実 API への依存をテストの必須条件にしない。
10. Debug / Release ビルド、既存自動テスト、実画面の基本操作を確認する。

**Phase 5 完了条件**：RSS / Atom と GitHub Releases が共通の Worker・通知基盤で動作し、同じリリースの再取得で無条件に新規通知を生成しないこと。

## 7. 対象外

- 一般 Web ページの汎用スクレイピング／差分監視
- Factorio MOD Portal
- 関心テーマに基づくニュース検索・推薦、情報源自動発見
- AI 管理コンソール、MCP / Tool Calling
- GitHub Issues / Projects の管理機能
- 高度な横断記事統合、全リリースの無制限バックフィル
