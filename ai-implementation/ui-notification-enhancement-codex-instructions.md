# Ateliers AI Assistant — 通知・情報収集 UI 再改修 Codex 実装指示

- 作成日: 2026-10-29
- 対象: `ateliers-ai-assistant` アプリケーションおよび `ateliers-ai-assistant-documents`
- 位置づけ: Phase 4 実装後の UI・通知管理機能の追加改修
- 基本方針: 既存の WinUI 3 / MVVM / Worker / SQLite / EF Core 構成を維持し、段階的に実装する。

## 1. 目的と前提

既存の通知・情報収集画面は、情報源、通知一覧、記事詳細の分離により改善済み。今回の目的は、常駐状態のグローバル操作と、通知の確認・後からの再参照・分類を実用的にすること。

着手前に現行コードと `ateliers-ai-assistant-documents/ui-design/`、`features/web-monitoring.md`、`features/web-monitoring-implementation-status.md`、`features/background-worker.md`、`data-design.md`、`architecture.md` を確認し、現状との相違があれば実コードを優先して差分を報告すること。既存の動作を推測で書き換えないこと。

## 2. 実装範囲

### 2.1 グローバルな稼働状態・操作

ナビゲーション下部の固定領域に、画面遷移によらず次を表示する。

- Worker 状態: 起動中／稼働中／停止中／接続不能／停止処理中など、取得できる実状態に応じて表示。
- Worker の開始・停止操作。設定画面の既存操作は残し、同じサービス・コマンドを使用する。二重実装しない。
- バックグラウンド AI の状態: 稼働可能／一時停止中／処理中／状態不明などを区別し、既存の一時停止・再開操作を利用する。
- Debug / Release 環境表示は既存の仕組みがあれば再利用する。
- 操作実行中は多重操作を防止し、成功・失敗・接続不能を表示する。ボタン操作だけで成功状態にしない。定期的な状態同期は既存の仕組みを利用し、過度なポーリングを増やさない。
- Worker 停止は RSS 巡回・AI 要約の両方を停止。AI 一時停止は RSS 取得を継続し、要約のみ停止するという既存の意味を維持する。実行中ジョブの扱いは既存仕様に従う。
- ナビゲーション幅が狭い場合も状態・操作を判別できること。誤操作しやすい配置やボタンの過密を避ける。

### 2.2 通知一覧の日付グループ化

- 通知を**記事の初回取得日時**で日付グループ化する。公開日時・要約完了日時とは区別する。
- 表示時はユーザーのローカル日付に変換し、「今日」「昨日」「YYYY/MM/DD」等の見出しで区切る。日付内は初回取得日時の降順を基本とする。
- 要約の遅延・再実行・一時停止／再開によって初回取得日時を変更しない。
- 現行 DB に保存されている日時の意味と型（UTC、オフセット等）を確認する。既存項目で実現できれば Migration は不要。既存の日時を推測で上書きしない。
- 一覧の更新時に選択記事、情報源、フィルター、詳細 WebView2 の表示・スクロールを不必要にリセットしない。

### 2.3 未読・既読

- 通知として**実際に一覧へ表示可能になった時点**で未読にする。要約待ちのまま一覧に存在しない記事は未読件数に含めない。
- 既存実装で要約待ちも通知として表示しているなら、表示対象になった時点で未読とする。表示開始の定義と通知生成タイミングを調査して明文化する。
- 既読状態は DB に永続化し、再起動・Worker 再接続後も維持する。候補は `ReadAt`（nullable）。実際のテーブル・エンティティに応じて最小変更で実装する。
- 記事詳細をユーザーが開いたとき既読にする。**単なる一覧の自動選択、一覧更新、初期選択では既読にしない。** 既読を未読に戻す明示操作を提供する。
- 未読とブックマーク／タグは独立。ブックマークやタグの操作だけで既読化しない。
- ナビゲーションの通知項目、情報源一覧、全体一覧に未読件数を表示する。未読件数は DB に存在する**全表示対象通知**から算出し、画面の最新100件制限に依存させない。削除済み情報源の通知は全体件数に含める。
- 一覧に未読・既読の視覚差を設ける（例: 未読ドット、文字の太さ）。色の違いだけに依存しない。
- 「すべて／未読／ブックマーク」の表示切替を提供する。未読の取得は全体最新100件のメモリ内絞り込みではなく、DB 側で条件を適用し最大100件取得する。
- 情報源別の絞り込みと組み合わせ可能にする。件数の集計条件と一覧の最大表示件数を UI で明示する。

### 2.4 ブックマーク

- 記事に ON/OFF のブックマーク状態を永続化する（候補 `IsBookmarked`、初期値 false）。既読・未読と独立。
- 一覧と記事詳細の双方から切替可能にする。アイコン操作は記事選択や既読化を発火させない。
- ブックマーク一覧は DB 条件で取得し最大100件表示する。**全体最新100件より古い記事も取得可能**にする。
- ブックマーク解除後の表示更新と選択維持を適切に扱う。ブックマークの日時、フォルダー、色、メモは今回追加しない。

### 2.5 手動タグ

- 1記事に複数のタグを付与できるようにする。タグは情報源とは別概念であり、情報源名を自動付与しない。
- `Tags` と記事との関連テーブル（例: `ArticleTags`）を使う多対多の正規化構造を基本とする。ただし現行 DB の実際のエンティティ・通知と記事の関連を調査し、**ユーザーが整理する対象の記事**へ安定して紐づく設計を選ぶ。既存命名規則に合わせる。
- 同一記事への同一タグの重複を防ぎ、タグ名の空白・前後空白・最大長・重複判定（大文字小文字の扱い）を明確にする。タグの追加・解除はトランザクション整合性を保つ。
- 記事詳細からタグの追加（新規作成または既存選択）・解除・一覧表示を可能にする。タグを選ぶと該当記事へ絞り込めるようにする。
- タグによる記事取得も DB 側で条件を適用し最大100件表示する。情報源との併用、既読／ブックマーク条件との組み合わせは操作が煩雑にならない最小 UI にする。
- タグ名変更・タグ自体の一括削除・階層・色・AI 自動タグ付け・自動分類は今回は不要。不要になった孤立タグの保持・扱いは設計文書で明示する。

### 2.6 削除・再取得との整合性

- 既存の個別／一括記事削除を維持する。削除時は既読・ブックマーク・記事タグ関連も整合的に削除する。共有タグ定義は他記事から使用中なら削除しない。
- 一括削除の確認画面に、対象記事数に加えてブックマーク付き記事数・タグ付き記事数を表示する。誤削除防止を優先する。
- 削除後に同じ記事が RSS の最新10件に再出現した場合、既存仕様どおり新規として取得し、未読・ブックマーク OFF・タグなしにする。
- 巡回履歴は記事削除後も保持する。既存の Markdown ファイル、通知、重複判定記録の削除仕様を壊さない。

## 3. データ・API・Migration 方針

- 既存 DB のエンティティ、インデックス、通知生成タイミング、API DTO、UI 更新フローを先に調査する。
- `ReadAt`、`IsBookmarked`、タグ関連を最小限の Migration で追加する。既存記事の `ReadAt` 初期値は**原則 NULL（未読）**とするが、既存データの一括未読化による影響を確認し、移行方針を報告してから確定する。`IsBookmarked` は false、タグ関連は空。
- UTC 等の保存規約は既存方針に合わせ、画面でローカル時刻へ変換する。タイムゾーンを暗黙に混在させない。
- Worker と Desktop が異なるプロセスであることを前提に、DB への直接アクセスの責務、API 更新・取得の境界、並行更新を既存アーキテクチャに合わせる。Desktop からの無秩序な DB 書込みを追加しない。
- 状態更新の成功／失敗は API の実結果で判定し、失敗時の画面表示を整える。未読件数やタグ関連の N+1 クエリ、過剰な全件読み込みを避ける。
- 既存の `FeedSourceUrl`、記事 URL、情報源削除後の通知閲覧、最新100件の制約を維持する。
- Migration のロールバック・Debug/Release 分離・既存データ互換性を確認する。既存 DB を破壊的に初期化しない。

## 4. UI 設計・操作性

- `ateliers-ai-assistant-documents/ui-design/` を基準とし、現在の WinUI 3 の UI を継続する。Blazor への移行は行わない。
- 情報源ペイン・通知一覧・記事詳細の現行構造を活かす。日付見出し、未読マーカー、ブックマーク、タグは情報密度を増やしすぎず配置する。
- 小さいウィンドウ幅、キーボード操作、スクロール、空状態、通信失敗、Worker 停止状態を確認する。
- UI と Worker の状態を共有する仕組みは既存サービスを再利用する。表示用のローカル状態を真実の情報源にしない。
- 読みやすさと操作の明確さを優先し、全面的な配色変更や他画面の再設計はしない。

## 5. 実装順序と確認ポイント

1. **事前調査**: DB・DTO・API・通知の生成タイミング、既存 UI の選択挙動、Worker 状態連携、削除処理を確認し、追加カラムと Migration の計画を短く報告。重大な仕様不一致があれば相談する。
2. **データ基盤**: 未読・ブックマーク・タグの永続化、API/DTO、Migration、削除時の整合性、テスト。
3. **通知 UI**: 日付グループ化、未読表示と件数、表示フィルター、ブックマーク、タグ編集・絞り込み。
4. **グローバル操作**: ナビゲーション下部の Worker／AI 状態と操作を追加。既存設定画面と状態を同期。
5. **回帰検証**: Debug/Release ビルド、既存＋追加テスト、Worker 接続／停止／再起動、複数幅、DB 移行、実画面、再取得・一括削除。
6. **文書更新**: `features/web-monitoring.md`、実装状況、`data-design.md`、UI 設計資料、必要なら `architecture.md` を実装結果に合わせて更新。

## 6. 必須テスト観点

- 新規通知の未読登録、ユーザーが詳細を開いた時の既読化、初期選択だけでは既読化しないこと、未読への戻し、再起動後の復元。
- 未読件数（全体・情報源別・削除済み情報源）、100件を超える未読／ブックマーク／タグ対象の DB 側検索。
- 要約待ちが通知一覧に存在しないときは未読件数に含めないこと。要約完了後の通知生成と状態反映。
- ブックマーク操作で既読状態が変わらないこと、タグ操作で既読化しないこと。
- タグ複数付与、既存タグ再利用、重複防止、絞り込み、削除時の関連整合性。
- 一括削除のブックマーク・タグ件数警告、削除後の再取得で新規状態へ戻ること。
- Worker 開始／停止、AI 一時停止／再開、接続失敗時の表示、設定画面とナビゲーション下部の状態一致。
- 日付境界、タイムゾーン、要約完了日時の変化で記事のグループが移動しないこと。
- 編集中の設定・選択記事・スクロール位置が定期更新で不必要に失われないこと。

## 7. 明示的な対象外

- AI 管理コンソール、Tool Calling、MCP、AI によるタグ自動付与。
- タグ階層、タグ色、記事メモ、ブックマークフォルダー、ブックマーク日時。
- Windows トースト通知、ゲーム検出による AI 自動停止、全件既読、全文検索、無制限ページング。
- 既存チャット、モデル管理、ログ画面の大規模な改修。

- 実行したビルド・テスト結果、未実施の手動検証、既知の制限。
- 変更ファイル一覧、UI 設計資料との相違点、後続課題。
