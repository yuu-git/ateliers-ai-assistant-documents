# Phase 4 — 常駐・自動巡回：Codex 実装指示

作成日: 2026-10-29  
対象: Ateliers AI Assistant（WinUI 3 / .NET / SQLite・EF Core / Ollama）

## 0. 作業開始前に

既存のアプリ本体および `ateliers-ai-assistant-documents` の現行ソース・設計文書を確認し、実際のプロジェクト構成・Phase 3 実装に合わせて実装してください。本文は実装方針であり、既存コードと矛盾するクラス名・パス・API を推測で固定しないでください。既存の Phase 1〜3 の動作を壊さず、必要な変更は小さな単位に分割してください。設計上の不明点や重大なトレードオフが判明した場合は、実装前に質問してください。

## 1. 目的と完了条件

### 目的

- UI と独立した**ユーザーセッション常駐 Worker**で Web 情報収集を実行する。
- UI から localhost API を通じて、情報源設定・巡回周期・自動巡回 ON/OFF・手動実行・状態表示・通知/履歴/記事削除を扱えるようにする。
- RSS 取得と Ollama 要約を分離し、ユーザーが GPU/CPU リソースを優先的に使えるようにする。
- 停止・再起動・障害後も、重複通知を避けながら処理を復旧できるようにする。

### 必須完了条件

1. ユーザーが Windows にサインインした状態で、**WinUI ウィンドウを閉じても Worker が生存し、自動巡回が継続する**。
2. Windows サインアウト後の動作は対象外。次回サインイン時には Worker が起動し、自動巡回が復旧する（初回導入・起動登録方法を含めて確認）。
3. 同じ RSS 記事を繰り返し取得しても、削除されていない通知済み記事を無条件に再通知しない。
4. AI 処理の一時停止中でも RSS の取得・新着記事の永続化は継続し、再開後に要約待ちを処理できる。
5. Debug / Release の保存先、Worker インスタンス、API 接続先が衝突しない。
6. UI が Worker に接続できない場合も、チャット等の無関係な機能は使用でき、状態と対処を表示できる。
7. UI からアプリケーションログとシステムログを区別して閲覧し、選択内容をテキストコピーできる。Worker 停止時も保存済みログを確認できる。

## 2. 実行方式とプロセス境界

- **Windows Service は今回採用しない。** Worker は現在サインインしているユーザーの権限で動く独立プロセスとする。UI プロセスの子として UI 終了時に巻き添え終了しない設計にする。
- サインイン時の自動起動を提供する。スタートアップ登録方式（タスクスケジューラ、ユーザー Run キー、Startup など）は現在の配布形態・権限・パッケージ化状態を確認して選定し、登録・解除・失敗時の挙動と手順を文書化する。管理者権限を不要に要求しない。
- Worker はユーザーセッション内で単一インスタンスとする。重複起動を検知し、二重巡回を防止する。UI の多重起動や Worker の再起動でも整合性を維持する。
- Windows 起動直後でなく**サインイン後**の開始であることを UI とドキュメントで明示する。
- UI は Worker の起動状態・最終疎通・実行状態・直近エラーを表示できるようにする。Worker が起動していない場合の開始方法も検討し、初回導入で操作不能にならないようにする。

## 3. データ保存・所有権・責務分離

- 既存の保存方針を維持する。
  - Release: `%APPDATA%\Ateliers-Dev\Ai-Assistant` / `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant`
  - Debug: `%APPDATA%\Ateliers-Dev\Ai-Assistant.Debug` / `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant.Debug`
  - テスト: 独立した一時領域
- Web 情報収集の DB 更新・Markdown 書き込み・通知登録・記事削除は**原則 Worker 側の Application Service 経由**に集約する。UI と Worker が同一データを無調整で更新しない。
- AI チャットの会話履歴やモデル検証 UI は今回 Worker へ移さない。既存チャットを維持する。
- 既存 DB を利用する場合は EF Core Migration と既存データの保持・アップグレードを確認する。Worker/UI 同時起動時の Migration 競合を防ぐ。
- SQLite のロック、トランザクション、ファイル保存と DB 更新の部分失敗を考慮する。Markdown の一時ファイル→確定配置、再実行時の修復など、既存の Phase 3 設計に沿って整合性を保つ。
- 既存の設定画面にある「保存先をエクスプローラーで開く」機能は維持し、Worker が保存した Markdown やログにも到達できるようにする。

## 4. localhost API と安全性

- UI↔Worker の通信は loopback (`127.0.0.1` / `::1`) 限定とし、LAN や外部へ公開しない。開発/本番のポート・名前付きエンドポイントは競合しないよう分離する。
- ローカルであっても**他のローカルプロセスや Web ページからのアクセスを無条件に信頼しない**。認証方式（ユーザー別の秘密トークン等）、Origin/CORS、CSRF 相当のリスク、トークンの保管権限を検討し、実装理由を文書化する。単に CORS を無効化するだけで安全とは扱わない。
- API の責務は情報源 CRUD、周期・自動 ON/OFF、AI 一時停止、手動巡回、状態照会、履歴・通知・記事削除等。実際の API 契約は既存 DTO と共通サービスを再利用し、UI が DB を直接操作しないよう整理する。
- 入力値の検証、エラー応答、タイムアウト、キャンセル、重複要求時の冪等性を設計する。ログに認証トークン・画像本文・機密情報を出さない。
- 外部から受け取る RSS URL に対しては SSRF 対策を考慮する（localhost、プライベートアドレス、リンクローカル、リダイレクト先等）。既存の情報源を壊さない範囲で安全な取得ポリシーを定める。

## 5. 情報源とスケジューラ

- Phase 3 の RSS/Atom 取得、最新10件制限、重複検出、Ollama 要約、Markdown 保存、通知フィード、巡回履歴、複数選択削除・再取得を継承する。
- 情報源ごとに RSS URL、名称、巡回周期（分）、自動巡回 ON/OFF、最終巡回日時、次回予定、実行状態・最終結果を扱えるようにする。**初期周期は60分**を提案値とし、極端に短い周期はバリデーションする。
- 手動実行は自動巡回 OFF でも可能とする。ただし同一情報源の実行中に重ねて処理しない（既存実行を返す、実行中を通知する等）。
- 起動時は保存済み設定から予定を再構成し、期限超過の情報源は**最大1回の追いつき実行**とする。停止期間中の予定回数をすべて再生しない。
- 同時実行数を制限し、複数情報源の巡回・要約が CPU/GPU・ネットワークを圧迫しないようにする。初期実装は逐次実行でもよい。
- ネットワーク失敗、RSS パース失敗、タイムアウト等は履歴とログに記録し、次回予定で再試行する。短時間の無限リトライを避ける。

## 6. RSS 収集と AI 要約の分離【重要】

- **RSS 取得・記事メタデータ永続化**と**Ollama 要約・Markdown 保存・通知**を独立した処理段階にする。
- 新着記事を取得した時点で、要約未完了でも記事の識別子、元 URL、タイトル、公開日時、フィードに含まれる要約対象テキスト等、後続の要約に必要な情報を永続化する。これにより、配信元の「最新10件」から外れても要約待ちを処理できる。
- 記事状態は最低限、要約待ち／処理中／完了／再試行可能な失敗を区別する。既存 Phase 3 の状態モデルを再利用・拡張する。
- 失敗時は「取得済み」だけで処理完了と判定せず、次回の再試行対象とする。正常完了記事の通知は重複生成しない。
- 処理中に Worker が強制終了しても、次回起動時に処理中状態を回復・再試行できるようにする。DB とファイルの整合性を確認する。
- AI 処理が一時停止中、Ollama 未起動、モデル未ロード、要約エラーのいずれでも、RSS の取得処理は継続可能とする。

## 7. Ollama とリソース制御【重要】

### 7.1 Ollama サーバー

- 既存の `localhost:11434` の Ollama サーバーを共有する。**Worker は Ollama サーバープロセスの起動・停止を行わない。**
- Worker 側で使用する要約モデルは明示的に設定可能とし、チャット画面の「最後に選択したモデル」とは独立させる。未設定・モデル削除・サーバー不在時は待機/失敗状態を明示する。

### 7.2 モデルの自動ロード・アンロード（初期値は両方 OFF）

- 設定項目:
  1. **バックグラウンド Worker によるモデルの自動ロードを許可**: 初期値 OFF
  2. **バックグラウンド Worker によるモデルの自動アンロードを許可**: 初期値 OFF
- 「ロード OFF」は**未ロードのモデルへ `/api/chat` を送らない**ことを意味する。Ollama はチャット要求自体でモデルをロードし得るため、`/api/ps` 等でロード状態を確認してから処理する。確認と送信の間の競合は完全に防げないことを文書化する。
- 「ロード ON」は Worker が要約に必要な場合だけモデルを利用/ロードすることを許可する。サーバーの起動権限とは別。
- 「アンロード OFF」は Worker から明示的なアンロード要求（例: `keep_alive:0`）を送らないことを意味する。ただし Ollama 自身のタイムアウトによる自動解放までは保証しない。
- 「アンロード ON」でも、Worker の処理開始前からロード済みだったモデルは明示的にアンロードしない。Worker が今回新規にロードしたと確認できたモデルだけを解放候補とする。ただし Ollama API は他プロセスの利用を厳密に把握できず、**他アプリへ影響するリスクが残る**ため、注意文を表示する。
- 既存 AI チャットのモデル管理と競合し得るため、同一アプリ内の Worker と UI 間で最低限のモデル使用調整を設計する。**他アプリとの完全な排他保証をうたわない。**
- 設定画面には各項目の意味と、GPU/メモリ消費・他アプリへの影響・Ollama 自身の自動アンロードの注意点を説明する。

### 7.3 バックグラウンド AI 処理の一時停止（Phase 4 必須）

- **「バックグラウンド AI 処理を一時停止」**の ON/OFF 操作を UI に設ける。初期値は**停止しない（AI 処理有効）**。
- 一時停止中も RSS の定期取得・重複検出・新着記事の永続化は継続し、**Ollama 要約は開始しない**。既に開始済みの要約については、キャンセルするか完了を待つかを設計して UI に明示する。リソース解放を優先するなら、可能な範囲で安全にキャンセルする方式を検討する。
- 再開後は要約待ち記事を順次処理する。未処理件数・一時停止状態・最後のエラーを UI に表示する。
- 一時停止状態は永続化し、Worker 再起動・Windows 再サインイン後もユーザーの意思を維持する。**一時停止中に自動ロード設定が ON でもモデルをロードしない。**
- これは情報源ごとの「自動巡回 ON/OFF」と別のグローバル設定であることを UI で明確にする。手動巡回時も RSS 取得は可能だが、AI 一時停止中は要約を行わない。
- 将来のゲーム起動検知や CPU/GPU 使用率に基づく自動停止は今回対象外。

## 8. UI 要件

- 情報源の追加・編集・削除、巡回周期、自動巡回 ON/OFF、手動実行、最終実行結果・次回予定・Worker 接続状態を分かりやすく表示する。
- 設定画面には、Worker の状態、要約モデル、モデル自動ロード/アンロードの独立設定、AI 処理一時停止、保存先をエクスプローラーで開く機能を配置する。配置は既存 UI に合わせて調整する。
- 「AI 処理を一時停止しても RSS の収集は継続します」「モデル自動ロード OFF では、未ロードのモデルを要約のために起動しません」「アンロードは他アプリへ影響する場合があります」等の説明を画面/ツールチップで表示する。
- 記事の個別・一括削除、通知・Markdown・重複記録の削除、巡回履歴保持、次回最新10件に含まれれば新規として復活する Phase 3 の動作を維持する。Worker への移管によって削除中の巡回競合を起こさない。
- Worker 不在時、要約待ち、停止中、取得失敗、要約失敗、実行中を区別し、誤解を招く成功表示を避ける。

## 9. ログ閲覧・トラブルシューティング画面【Phase 4 追加必須】

### 9.1 目的・分類

- UI に **「ログ」画面**を追加し、タブ等で **「アプリケーションログ」** と **「システムログ」** を切り替えられるようにする。既存のナビゲーション設計に自然に組み込む。
- **アプリケーションログ**は利用者が運用状況を把握するための記録。例: 情報源の巡回開始/終了、取得・新規・重複件数、要約完了/保留/失敗、手動実行、AI 処理一時停止/再開、記事削除結果。
- **システムログ**は開発・障害調査用の技術的記録。例: UI/Worker 起動・終了、localhost API 疎通・認証失敗、SQLite/EF Core、Ollama HTTP 通信、例外、リトライ、内部状態遷移。
- 「アプリケーションログ」「システムログ」は **OS の Windows イベントログではなく、本アプリが記録するログの表示分類**であることを UI またはドキュメントで明確にする。
- 既存 Phase 2 のログ実装を確認し、可能な限り再利用する。カテゴリごとに独立したログ基盤を新設するのではなく、**共通の構造化ログに分類情報を付与**して扱う。既存のファイル形式・ライブラリと矛盾しない最小限の拡張とする。

### 9.2 画面・操作

- 日時（ローカル表示とタイムゾーンの扱いを明確化）、ログレベル、発生元（UI / Worker / コンポーネント）、メッセージを一覧表示する。必要に応じて詳細欄に例外情報や相関 ID を表示する。
- 一覧は日時降順を基本とし、**レベル・期間・キーワードの簡易絞り込み**を提供する。大量ログを一括でメモリに展開せず、直近 N 件の取得またはページングなどで負荷を制御する。
- **選択行のコピー、複数行のコピー、詳細テキストのコピー**を可能にする。コピー文字列は日時・レベル・発生元・メッセージを含む読みやすいプレーンテキストとする。複数選択が既存 UI と合わない場合は「表示中をコピー」等の代替操作を用意する。
- 手動更新を提供する。自動更新は必須とせず、導入する場合も UI 負荷と選択状態に配慮する。
- **ログ保存フォルダーをエクスプローラーで開く**操作を設け、既存の設定画面のフォルダー表示機能を再利用する。保存先の変更機能は不要。
- Worker に接続できないときでも、**既に永続化されたログの閲覧・コピーは可能**とする。Worker の稼働状態を誤って正常と表示しない。

### 9.3 保存・プロセス間連携・安全性

- Debug / Release のログは既存の `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant[.Debug]` 配下で分離する。UI と Worker のログを画面上で統合して閲覧できるようにするが、**複数プロセスが同じファイルへ無調整で追記する設計は避ける**。プロセス別ファイル + 共通閲覧、あるいは既存基盤に適した安全な方式を選ぶ。
- 既存のログ出力を破壊せず、ログファイルのローテーション・保存上限・古いファイルの削除方針を明示する。DB にログ全文を重複保存する必要はない。実装形式は既存コードに合わせて判断する。
- ログ閲覧画面が Worker の localhost API に依存して停止しないよう、読取専用のログ閲覧サービス等で責務を整理する。ファイル書込中・ローテーション中の読取や部分行は安全に扱う。
- API 認証情報、秘密トークン、認証ヘッダー、個人情報、チャット本文、画像 Base64、RSS の全文などを不用意にログへ記録しない。**例外の詳細をシステムログへ出す場合も秘密情報をマスク**する。ログコピーは利用者の明示操作のみ。
- 利用者向けのログ文言は簡潔で分かりやすくし、詳細なスタックトレース等はシステムログに分離する。両分類に同一イベントを記録する場合は二重保存を避けられる設計を検討する。

## 10. 障害復旧・運用

- Worker の通常終了・異常終了・OS 再起動時の復旧を設計する。ユーザーサインイン時の自動起動と、起動登録が無効な場合の案内を実装する。
- 失敗時に再試行するが、再通知や二重 Markdown 生成を避ける。処理中フラグが永続的に残らないよう復旧処理を設ける。
- UI から手動実行を要求しても Worker が不在なら、明確なエラー/復旧導線を表示する。
- API、Worker、Ollama、DB のエラーを区別してログに記録し、Debug / Release のログを分離する。過剰なログ蓄積への対応を検討する。
- Worker と UI のバージョン不一致、DB Migration の順序、起動直後の API 未準備、Windows スリープ復帰も考慮する。

## 11. テスト・受け入れ確認

既存テストを維持し、可能な限り自動テストを追加してください。少なくとも次を検証してください。

1. UI を閉じても Worker が動き、短い検証周期で巡回が継続する。
2. サインアウト→再サインイン、または PC 再起動相当の手順で Worker が復旧する。
3. 同一記事の再取得で通知が増えない。Phase 3 の記事削除→再取得も維持される。
4. AI 一時停止中は RSS 収集と記事保存が継続する一方、Ollama への要約要求は発生しない。再開後に待機記事が処理される。
5. 自動ロード OFF でモデル未ロードなら、要約リクエストによる暗黙ロードを行わない。ロード済みモデルは使用できる。
6. 自動アンロード OFF では明示的アンロード要求を出さない。ON の場合も既存ロード済みモデルは解放対象外。
7. Ollama サーバー不在、タイムアウト、モデル削除、Worker 強制終了、DB 一時ロック、Markdown 保存失敗で取りこぼし・重複通知を防ぐ。
8. 同一情報源の手動/自動同時実行、Worker 二重起動、UI 二重起動で重複実行しない。
9. Debug / Release の Worker・API・DB・設定・Markdown・ログが分離される。
10. UI の設定画面から実際の保存先を確認・エクスプローラーで開ける。保存先の手動変更はできない。
11. localhost API が LAN から接続できず、無認証/不正な要求が保護される。
12. ログ画面でアプリケーション/システム分類、UI/Worker の記録、レベル・期間・キーワード絞り込み、更新、コピー、ログフォルダー起動を確認する。Worker 停止中でも保存済みログを読める。
13. ログのローテーション中・書込中の読み取り、大量ログ表示、機密情報マスキング、Debug / Release 分離を確認する。
14. Debug / Release ビルドと既存・追加テストが成功する。

実機での Windows サインイン時自動起動やスリープ復帰など、自動テストだけでは確認しづらい項目は**手動検証手順と実施結果**を残してください。実際に未確認の項目を確認済みと報告しないでください。

## 12. 非対象（スコープ拡大を避ける）

- Windows Service / LocalSystem / サインアウト中の稼働
- Ollama サーバーそのものの自動起動・停止
- GPU 使用率やゲーム起動検知による AI 自動停止
- AI 管理コンソール、MCP、自然言語による設定変更
- Web ページ本文の高度な抽出、無制限の RSS 取得、外部公開 API
- OS トースト通知、クラウド同期、複数ユーザー間の共有
- AI チャットの Worker 化・フルチャットアプリ化

## 13. ドキュメントと完了報告

- `architecture.md`、`roadmap.md`、Web 監視関連の設計/実装状況、データ保存方針、ログ閲覧機能の仕様、必要なら API 契約と Worker 運用手順を更新する。
- Worker の起動登録/解除、開発時の起動方法、API の疎通、障害時の復旧、Debug / Release 分離を文書化する。
- 実装差分の概要、設計上の判断、テスト結果、実機確認結果、残課題を報告する。
- ユーザーが今後利用することを考え、AI 一時停止とモデルロード/アンロードの説明を UI とドキュメントの双方に残す。

**判断優先順位:** ユーザーのリソース制御 ＞ 収集データの取りこぼし防止 ＞ 重複通知防止 ＞ 実装の簡潔さ。これらが衝突する場合は、勝手に仕様を決めずに確認してください。
