# Codex 実装指示 — Phase 2: 履歴と共通基盤

## 対象リポジトリ

アプリケーション:
`yuu-git\ateliers-ai-assistant`

設計ドキュメント:
`yuu-git\ateliers-ai-assistant-documents`

## 作業開始前の確認

1. アプリケーションの現行ソースと README を確認してください。
2. 設計ドキュメントの `README.md`、`requirements.md`、`architecture.md`、`repository-structure.md`、`roadmap.md`、`data-design.md`、`development-guidelines.md`、`features/ai-chat.md`、および保存方針 [data-storage-policy.md](data-storage-policy.md) を確認してください。
3. Phase 1 の機能（Ollama 通信、モデル管理、ストリーミング、Markdown、画像貼り付け、終了時アンロード、貼り付け競合対策）を維持してください。
4. 現行の実装と指示に矛盾や不明点がある場合、仕様を独自に確定せず実装前に確認してください。

## 目的と範囲

Phase 2「履歴と共通基盤」を実装してください。

- SQLite / EF Core による **必要な会話だけの保存・再開・削除**
- 将来の通知・メッセージ表示に備えた、必要最小限の DTO／契約整理
- 設定・ログ・例外処理・テストの拡充
- **設定画面からアプリデータの保存先を表示し、エクスプローラーで開く機能**

Phase 2 はチャットアプリの高機能化を目的としません。ChatGPT のようにアプリ全体のナビゲーションに会話スレッドを並べないでください。

## 1. 会話履歴のユーザー体験

### チャットを開いたとき

- AI チャット画面内で「新しい会話」と「保存済みの会話」を選べるようにしてください。
- 保存済み会話は一覧で表示し、タイトル・更新日時・使用モデル等、識別に必要な情報を示してください。
- 一覧から会話を選択すると、過去のメッセージと画像を復元して会話を継続できるようにしてください。
- 会話一覧は AI チャット機能の内部に置き、アプリ全体の NavigationView にスレッドを追加しないでください。
- 保存済み会話が0件でも自然に利用できる空状態を用意してください。

### 保存ルール

- 「新しい会話」はメモリ上で開始し、空スレッドを DB に作らないでください。
- 未保存会話は明示的な「会話を保存」操作が行われるまで DB に保存しません。
- 保存時にスレッド名を指定・変更できるようにしてください。初期タイトルの提案は可能ですが、LLM による自動命名は必須ではありません。
- 保存済み会話を再開した後のメッセージ追加・更新は自動保存してください。
- 自動保存失敗時は保存済みと誤表示せず、失敗を通知し、可能な限りメモリ上の会話を維持してください。
- 未保存会話からの切り替え、画面離脱、アプリ終了時に未保存内容が失われる場合は「保存」「保存せず破棄」「キャンセル」を選べるようにしてください。**非同期保存を要する終了処理は WinUI 3 のライフサイクルに適した方法で実装し、確認前に終了させない**でください。
- 強制終了・クラッシュ時の未保存会話復元は対象外です。
- 既存の「新しい会話」操作との整合性を保ってください。

### 削除ルール

- 保存済みスレッド単位で削除できます。
- 削除前に確認ダイアログを表示してください。
- 配下のメッセージ・添付画像を一括削除してください。
- 個別メッセージ削除、復元、ごみ箱、全文検索、自動削除は実装しません。

### モデルの扱い

- 保存済み会話のモデル情報を保持してください。
- 会話再開時、保存モデルが現在の Ollama に存在しない・ロードされていない・選択中モデルと異なる場合を適切に扱ってください。無断でモデルをダウンロードしないでください。
- モデル切り替えや終了時アンロードなど Phase 1 の管理動作と矛盾しないようにしてください。

## 2. データ設計と永続化

- SQLite と EF Core を使用してください。
- スレッド、メッセージ、画像を表現できる最小限のスキーマを設計してください。
- メッセージの順序、Role、Markdown 原文、作成日時、必要なモデル情報を保持してください。
- 画像は Base64 文字列ではなく BLOB として保存することを基本としてください。
- 画像は現在の 1メッセージ1枚・長辺1536px の制約を維持し、保存済み会話を再開した後の Ollama リクエストでも必要に応じて再送信できるようにしてください。
- スレッド削除時は関連データが残らないよう外部キー／カスケード削除等を適切に設定してください。
- DB アクセスは ViewModel から分離し、Application の契約と Infrastructure の実装を適切に配置してください。
- EF Core Migration を導入し、既存データを無条件に削除する初期化は行わないでください。
- DB ファイルのロック、破損、アクセス拒否、マイグレーション失敗などで UI 全体がクラッシュしないよう、エラー処理を設けてください。
- 会話の原文は保存し、HTML や WebView2 の DOM を永続化しないでください。

## 3. 保存先と設定画面

新規保存方針ドキュメントに従い、保存先を次のように固定してください。

以下は Release 用の保存先です。後続の確認済み追加要件として、Debug は Roaming / Local ともに `Ai-Assistant.Debug` に分離します。既存データを移動・コピーせず Release 用に維持し、設定画面に使用中のデータ環境を表示します。詳細は [保存方針](data-storage-policy.md#debug--release-の分離2026-10-29-追加) を参照してください。

- 設定: `%APPDATA%\Ateliers-Dev\Ai-Assistant\settings.json`
- DB: `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\data\assistant.db`
- ログ: `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\logs\`
- キャッシュ: `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\cache\`

### 設定画面に追加する機能

- 「データ保存先」セクションを設けてください。既存の設定画面があればそこに統合し、なければ最小限の設定画面を作成してください。
- Roaming 設定、Local アプリデータ、会話履歴 DB 格納フォルダー、ログフォルダーについて、実際に解決したパスを読み取り専用で表示してください。
- 各項目に「エクスプローラーで開く」操作を用意してください。必要であればパスのコピー操作も付けて構いません。
- **保存先を変更する UI や任意パスを設定する機能は実装しないでください。**
- フォルダーが存在しない場合の挙動を統一してください（開く操作時に対象フォルダーを作成する方式を推奨）。
- Explorer 起動失敗・アクセス拒否時はユーザーに通知し、アプリをクラッシュさせないでください。
- Explorer で開く対象はアプリ内部で解決した固定パスに限定し、外部入力を任意の実行引数に渡さないでください。
- パス解決を共通サービスへ集約し、DB・ログ・設定・画面表示が同じパスを利用するようにしてください。
- パッケージ化／非パッケージ化と Debug／Release で保存先が想定どおりか確認し、制約があれば報告してください。

## 4. 共通基盤

### 通知・メッセージ DTO／契約

- 将来の Web 情報収集や通知機能で再利用するため、通知内容、発生日時、種別、表示用本文等の最小限の契約を整理してください。
- 既存のチャット用メッセージモデルを通知用に無理に共通化しないでください。
- Web 収集、定期実行、通知配信、Windows Service の実体は実装しません。
- 将来利用を想定した抽象化は、実際の利用目的が説明できる最小限にとどめてください。

### 設定

- 小容量のユーザー設定を Roaming に保存する仕組みを整備してください。
- 初回起動時の既定値、設定ファイルが存在しない場合、不正な JSON、書き込み失敗を扱ってください。
- 機密情報を平文設定やログへ無条件に保存しないでください。
- 今回使わない設定項目を大量に追加しないでください。

### ログ・例外処理

- Local の `logs` 配下に診断ログを出力する仕組みを整備してください。
- ログが無制限に増えないようローテーションまたは保持期間を設定してください。
- 既定ではプロンプト全文、画像データ、認証情報などをログに出力しないでください。
- DB 保存失敗、設定読込失敗、Explorer 起動失敗等を適切に記録・通知してください。

## 5. テストと受け入れ条件

最低限、次を確認してください。

1. 新しい会話を開始しても DB に空スレッドが増えない。
2. 未保存会話は明示的に保存したときだけ永続化される。
3. アプリ再起動後に保存済み会話のテキスト・Markdown 原文・画像が復元される。
4. 復元した画像付き会話で後続メッセージを送信できる。
5. 保存済み会話への追記が自動保存される。
6. 未保存会話の切り替え・終了時に保存／破棄／キャンセルが正しく動作する。
7. スレッド削除でメッセージ・画像も削除される。
8. DB や設定ファイルの未作成・読込失敗・書込失敗を適切に扱う。
9. 設定画面のパスが実際の保存先と一致し、各フォルダーを Explorer で開ける。
10. 保存先変更機能が存在しない。
11. モデル選択・ロード／アンロード・終了時アンロードが正常に動作する。
12. Markdown・ストリーミング・画像貼り付け・Ctrl+V 競合修正に回帰がない。
13. x64 Debug ビルド、自動テスト、Release 発行を確認する。
14. データ移行、DB 補助ファイル、パッケージ化形態に関する既知の制約を README に記録する。

## 6. 実装しない機能

- チャットスレッドをアプリ全体のナビゲーションに表示する機能
- すべての会話の無条件自動保存
- 個別メッセージ編集・削除、全文検索、タグ、フォルダー分類
- 会話履歴のクラウド同期、エクスポート／インポート、バックアップ UI
- 画像の複数枚添付、画像編集、画像の自動永続化（未保存会話）
- 保存先変更 UI、任意パス設定
- Windows Service、Web 情報収集処理、MCP／管理コンソール

## 7. 進め方と報告

### 2026-10-29 の確認済み補足

- 中止・失敗したターンも表示状態ごと保存・復元し、次回の Ollama 送信履歴からは従来どおり除外する。
- 保存済み会話の回答は、完了・中止・失敗時にまとめて自動保存する。未送信の入力・添付も保存・復元し、その変更は遅延集約して自動保存する。
- Roaming 設定は最後に選択したモデルだけ。モデルが存在すれば起動時に選択を復元し、自動ロードはしない。
- EF Core のモデル構築・Migration の実行を保持するため、Release の `PublishTrimmed` は無効にする。発行サイズの増加を許容する。

- まず既存コードと設計書を確認し、必要な変更箇所、DB スキーマ、UI 遷移、ライフサイクル上の懸念を短く整理してください。
- 仕様が確定している範囲は実装を進めて構いません。重要な不明点は先に質問してください。
- 既存のプロジェクト分離・命名規約・DI・テスト方針に従ってください。不要なプロジェクトや過剰な抽象化を増やさないでください。
- 変更後は設計書・README・必要なテストを更新してください。
- 最後に、変更ファイル、追加 NuGet、Migration、実装した操作、テスト結果、Debug／Release の結果、未対応事項、運用上の注意点を報告してください。
