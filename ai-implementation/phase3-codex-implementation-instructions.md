# Codex 実装指示 — Phase 3: Web 情報収集 MVP

## 対象リポジトリ

アプリケーション:
`yuu-git\ateliers-ai-assistant`

設計ドキュメント:
`yuu-git\ateliers-ai-assistant-documents`

## 目的と位置付け

Ateliers AI Assistant の Phase 3「Web 情報収集 MVP」を実装してください。既存の Phase 1（Ollama チャット）および Phase 2（SQLite / EF Core、設定・ログ、通知・メッセージ共通契約、Debug / Release データ分離）の実装とドキュメントを確認し、既存構成に沿って最小限の変更で実装してください。

この指示は設計上の要件です。実際のクラス名、DB 構造、画面構成、既存 API はリポジトリを調査してから決定してください。既存の `roadmap.md`、`architecture.md`、`data-design.md`、`data-storage-policy.md`、`features/web-monitoring.md` 等があれば読み、差分や矛盾があれば先に報告してください。

## MVP スコープ

- RSS / Atom フィードを **1 件** 登録または入力し、UI から手動で取得できること。
- 取得した記事の重複を永続データで判定すること。
- 新規記事を既存の Ollama 接続機能を利用して要約できること。
- 要約結果を Markdown ファイルとして保存できること。
- 巡回実行履歴と通知フィードをアプリ内で確認できること。
- 同じフィードを連続実行しても、既に通知した記事を無条件に再通知しないこと。

**今回は実装しない:** 定期実行、Windows Service、複数フィード管理、Web ページ本文の高度な抽出、ブラウザー操作、MCP、AI 管理コンソール、通知の OS トースト連携、全文検索、クラウド同期、複雑なルールエンジン。

## 1. RSS 取得と正規化

- UI でフィード URL を設定・確認し、手動の「取得」操作を提供する。MVP は 1 件のフィードのみ対象とする。
- RSS 2.0 と Atom を可能な範囲で標準ライブラリ等を用いて解析し、記事の識別子、URL、タイトル、公開日時、概要を正規化する。
- フィードの XML に含まれる外部エンティティなどを安全に扱う。タイムアウト、キャンセル、応答サイズの上限、HTTP エラー、不正な XML、空フィードを適切に処理する。
- URL は HTTP / HTTPS のみを受け付け、ローカルファイル等の不適切なスキームは拒否する。取得先の安全性についてはローカルアプリの利用形態を踏まえて検討する。
- フィードの説明文・記事本文は外部の信頼できない入力として扱う。要約指示やアプリ内部操作への命令として実行しない。

## 2. 重複検出と処理状態

- 再起動しても有効な重複判定キーを DB に保存する。第一候補はフィード識別子と記事 GUID / Atom ID、欠ける場合は正規化した記事 URL、さらに必要な場合は安定した代替キーとする。
- URL 末尾の追跡パラメータ等をどう扱うかは、誤判定を避ける範囲で単純な規則に限定し、テストで確認する。
- DB の一意制約等で重複登録を防ぐ。重複記事を再取得しても、既存の通知レコードを無条件に再生成しない。
- 「取得した」「要約に成功した」「Markdown 保存に成功した」「通知を作成した」「失敗した」等の状態を混同しない。要約失敗や保存失敗が起きても、次回実行時に適切に再試行できること。
- 再試行時にも通知の重複を作らない。必要に応じて DB トランザクションや冪等な登録処理を使う。
- 記事が更新された場合の再要約・再通知は MVP では原則行わず、将来課題として記録する。

## 3. Ollama 要約

- Phase 1 の既存 Ollama 通信・モデル選択等の仕組みを再利用し、Web 収集用の Application Service から呼び出せるようにする。チャット画面や ViewModel に収集処理を直接実装しない。
- 記事タイトル、URL、公開日時、フィードが提供する概要・本文を材料に、日本語で簡潔な要約を生成する。
- フィードが概要しか提供しない場合、取得していない全文を読んだかのような要約を作らない。要約の入力範囲を明示できるようにする。
- モデル未選択、モデル削除、Ollama 未起動、タイムアウト、キャンセル、空応答等を扱う。失敗は巡回履歴に記録し、記事の再試行を可能にする。
- チャット履歴には Web 収集の要約依頼を混在させない。モデルの自動ロードやアンロードが他画面の使用と衝突しないよう、既存方針を尊重する。

## 4. Markdown 保存

- 保存先は `%LOCALAPPDATA%\Ateliers-Dev\Ai-Assistant\` 配下とし、既存のパス解決機構に従う。Debug は `Ai-Assistant.Debug`、Release は `Ai-Assistant`、自動テストは一時領域を使用する。
- 例: `web-monitoring/articles/` 配下に Markdown を保存する。最終的な命名は既存のデータ保存方針と整合させる。
- タイトル、元 URL、公開日時、取得日時、使用モデル、要約本文、情報源（フィードの概要に基づく等）を記録する。必要に応じて Docusaurus にも移しやすい形式とするが、Docusaurus への自動公開は行わない。
- ファイル名は記事 ID 等に基づく安全で安定した名前とし、パス走査やファイル名衝突を防ぐ。文字コードは UTF-8。
- Markdown 書き込みに失敗した場合は処理完了とせず、次回再試行できること。可能なら一時ファイルからの置換等で不完全ファイルを防ぐ。
- 既存の設定画面から Local 保存先をエクスプローラーで開ける機能は維持する。必要なら収集結果フォルダーを開く導線を追加してよいが、保存先の変更 UI は作らない。

## 5. 巡回履歴と通知フィード

- 実行ごとに開始日時、終了日時、成功/失敗、取得件数、新規件数、重複件数、要約成功/失敗件数、エラー概要などを確認できるようにする（項目は実装に合わせて合理化可）。
- 新規に要約・保存まで完了した記事について、既存の共通通知 DTO / 契約を利用してアプリ内通知フィードに表示する。
- 通知には記事タイトル、要約の一部、元 URL、日時、保存 Markdown への導線を持たせる。外部リンクは安全に開く。
- 既存通知は再取得時に重複追加しない。通知履歴は SQLite へ永続化する。
- 実行中の進捗・キャンセル・エラーを UI で把握できるようにし、画面操作をブロックしない。

## 6. データ・設定・責務分離

- 既存 EF Core / SQLite の DB、Migration、DI、設定、ロギングの実装方針に従う。既存 DB の会話履歴を壊さず Migration を適用できること。
- 記事、巡回実行、通知の責務を分け、重複判定キー・処理状態・一意制約を DB 設計に反映する。
- Core / Application / Infrastructure / Desktop の既存レイヤー境界を守る。UI は Application Service を呼び、RSS 取得・DB・ファイル保存・Ollama 通信の詳細は適切な層へ置く。
- RSS URL や要約に使うモデルの保存方法は既存設定機構と整合させる。モデルが利用できない場合の挙動を明確にする。
- 将来の複数フィード・スケジュール処理へ拡張可能な最低限の境界は設けるが、抽象化を増やしすぎない。

## 7. テスト・完了条件

最低限、以下を自動テストまたは手動テストで確認すること。

1. サンプル RSS / Atom を読み込み、記事を正規化できる。
2. 同じ RSS を **2 回連続で手動取得**しても同一記事の通知が重複しない。
3. アプリ再起動後の再取得でも同一記事の通知が重複しない。
4. 要約失敗後、次回実行で再試行でき、成功後の通知は 1 件だけとなる。
5. Markdown 保存失敗後も再試行可能で、成功した Markdown の内容と保存先が正しい。
6. 巡回履歴と通知フィードが再起動後も表示される。
7. Debug / Release / 自動テストの保存先が混在しない。
8. 不正 XML、HTTP エラー、タイムアウト、キャンセル、モデル未利用時にアプリがクラッシュしない。
9. Phase 1 のチャットと Phase 2 の会話保存・再開・削除に回帰がない。
10. Debug / Release ビルドと既存テストが成功する。

外部 RSS サイトや Ollama 実機に依存しないテストを優先し、HTTP 応答と要約結果はモック等で再現する。実サイト・実モデルによる E2E は別途手動確認する。

## 8. 実装の進め方と報告

1. 既存コードとドキュメントを調査し、実装方針・追加予定の DB エンティティ / Migration / UI / サービスを簡潔に提示する。
2. 仕様上の重大な曖昧さや既存設計との矛盾があれば、実装前に質問する。細部は既存規約に合わせて判断する。
3. 小さな単位で実装・テストする。必要に応じてドキュメント（Web 監視機能、データ設計、保存方針、ロードマップ等）を更新する。
4. 最後に変更ファイル、実装内容、動作確認手順、テスト結果、未対応事項、既知の制約を報告する。

**最重要の完了条件:** 同一フィードを 2 回実行しても、同じ記事を無条件に再通知しない。さらに再起動後も重複を防ぎ、途中失敗から安全に再試行できること。
