# Ateliers AI Assistant — Phase 6 Codex 実装指示

## 0. 依頼概要

Phase 5 とロードマップ・関連ドキュメントの更新は完了しています。次の **Phase 6「画面キャプチャ・Vision 解析 MVP」** を実装してください。

**目的:** ユーザーが任意の画面またはウィンドウを明示的に選択し、手動でキャプチャした画像をローカル Ollama の Vision 対応モデルへ送信して、解析結果をアプリ内で閲覧できるようにする。

Phase 7「継続画面監視・AI コメント MVP」へ発展可能な構成を意識しますが、**定期キャプチャ、常駐監視、AI の自動コメント投稿は今回実装しません**。

## 1. 最初に行う調査と報告（実装前）

実装前に、アプリケーション本体と `ateliers-ai-assistant-documents` の最新状態を確認してください。特に以下を調査し、**変更予定ファイル、方式、未解決事項を短く報告してから実装に着手してください**。重大な仕様判断が必要な場合は確認を求めてください。

- 現行ロードマップの Phase 6 / 7、MVP 到達条件、既存要件・アーキテクチャ文書。
- WinUI 3 の画面構成、ナビゲーション、既存 AI チャット、画像貼り付け、画像送信、Markdown 表示の実装。
- Ollama モデル一覧・選択・Vision 対応の判定方法、API クライアント、ストリーミング、キャンセル、例外処理。
- UI / Worker の責務、既存の AI 停止・負荷制御設定、DI、ログ、Debug/Release の保存先。
- Windows Graphics Capture 等の採用候補と、対象選択 UI の実現可能性・制約。

既存の設計を確認せずに新規フレームワークや重複するサービスを導入しないでください。

## 2. 実装範囲

### 2.1 画面・ウィンドウ選択

- ユーザーの明示操作で、キャプチャ対象の **ウィンドウまたはディスプレイ** を選択できること。
- Windows 標準の選択 UI（例: `GraphicsCapturePicker`）を第一候補とし、WinUI 3 デスクトップで必要なウィンドウハンドル初期化を適切に実装すること。
- 選択キャンセルは正常操作として扱い、エラー表示しないこと。
- キャプチャ対象の種類・名前等を可能な範囲で表示すること。取得できない情報を無理に推測しないこと。
- 対象が閉じられた場合、キャプチャ不可の場合、権限や OS 制約がある場合に適切なエラーを示すこと。
- アプリ自身を対象にした際の再帰的キャプチャなど、明らかな UX 問題に注意すること。

### 2.2 手動キャプチャ

- 選択済み対象に対して、ユーザーが **「キャプチャ」** を押したときだけ画像を取得すること。
- 取得した画像をアプリ内でプレビューできること。
- 解析実行前に画像を確認できること。プレビュー画像と解析に送る画像が一致すること。
- 一時的なキャプチャリソース、フレームプール、D3D 関連リソースなどは適切に解放すること。
- キャプチャを繰り返しても著しいメモリ増加やハンドルリークが起きないこと。
- 初期実装では画像を永続保存しないこと。明示的な保存機能も必須としない。
- 画面に機密情報が含まれ得るため、キャプチャ画像の内容や Base64 データをログに出さないこと。

**技術上の注意:** `Windows.Graphics.Capture` を優先候補としますが、単一フレームの取得方法や WinUI 3 / Windows App SDK との互換性を実際に検証してください。保護されたコンテンツ、最小化されたウィンドウ、一部ゲームの排他フルスクリーンなどは取得できない場合があります。MVP では通常のデスクトップウィンドウとディスプレイを基本動作対象とし、ゲーム対応を無条件に保証しないでください。

### 2.3 Ollama Vision 解析

- キャプチャ画像を既存 Ollama 連携経由で Vision 対応モデルへ送信し、ユーザーが指定したプロンプトに従って解析できること。
- 既存 AI チャットの画像入力・Ollama API 呼び出し・モデル選択・Markdown 表示などを可能な範囲で再利用すること。UI 依存ロジックの安易なコピーは避けること。
- Vision 対応モデルを選択できること。対応判定が信頼できない場合は、モデル能力の照会結果や既存仕様に従い、非対応時の API エラーをわかりやすく扱うこと。**モデル名の文字列だけで断定しないこと**。
- プロンプトはユーザーが編集可能にし、初期値は用途を限定しない一般的な画面説明・気付きの依頼とすること。
- 実行中表示、完了、失敗、ユーザーキャンセルを区別すること。可能なら既存のストリーミング表示を再利用すること。
- Ollama 未起動、Vision 非対応、モデル未ロード、通信エラー、タイムアウト等を適切に扱うこと。
- 既存の AI 一時停止やリソース制御の意図を尊重し、停止中に無断でモデルを起動しないこと。
- 二重クリック等による重複解析を防ぎ、UI スレッドをブロックしないこと。

### 2.4 UI / UX

- 既存の WinUI 3 ダークテーマ、ナビゲーション、余白・コンポーネント設計と整合させること。
- Phase 6 の機能を見つけやすい独立した画面または既存画面の適切な導線として追加すること。**既存 AI チャットをモデル動作確認用途として維持する**こと。
- 基本操作の順序を「対象選択 → 手動キャプチャ → プレビュー → プロンプト指定・モデル選択 → 解析 → 結果表示」とすること。
- 対象未選択、画像未取得、モデル未選択などの状態に応じて操作を無効化し、何をすればよいか明確にすること。
- 結果は既存の Markdown 表示コンポーネントを可能な範囲で再利用すること。
- 現時点で Slack / Teams 風の継続コメント履歴 UI は不要。これは Phase 7 の対象とする。
- ウィンドウサイズ変更時にも、プレビュー・操作・結果が極端に崩れないこと。

## 3. アーキテクチャ上の境界

- キャプチャ処理は UI イベントハンドラに直接詰め込まず、適切なインターフェース / サービスへ分離すること。ただし将来のためだけの巨大な抽象化は避けること。
- **対象選択と Windows デスクトップキャプチャはユーザーセッション側の責務**とし、既存 Worker へ無条件に移さないこと。
- Vision 解析は既存の Ollama / Application Service の責務と整合させること。
- 将来 Phase 7 で、手動実行を定期実行に差し替えられる程度の責務分離を意識すること。ただしスケジューラ、常駐 Capture Agent、画像差分検出、監視履歴 DB は実装しないこと。
- 既存の DB スキーマ変更は原則不要と想定する。必要と判断した場合は理由・Migration・既存データへの影響を事前報告すること。
- 画面キャプチャはユーザー操作を起点とし、裏で自動取得しないこと。

## 4. 明確な対象外

以下は **Phase 7 以降または時期未定** です。

- 10 秒おき等の定期キャプチャ、バックグラウンド継続監視。
- UI を閉じてもキャプチャし続ける常駐 Agent / Worker 拡張。
- 画像差分・イベント検出、AI による自律的な監視条件変更。
- AI からの定期的・自発的なコメント投稿、Slack / Teams 風の監視会話履歴。
- 音声生成・再生、音声通知。
- ゲーム固有の解析、OCR 専用パイプライン、画面内 UI 要素の自動操作。
- 長期コンテキスト管理、VS Code のソース・文書の意味解析専用機能。
- AI 管理コンソール、MCP 動画生成連携、汎用 Web 監視。

## 5. テスト・受け入れ条件

最低限、次を確認してください。

1. 一般的なアプリのウィンドウを選択し、手動キャプチャしてプレビューできる。
2. ディスプレイを選択し、手動キャプチャしてプレビューできる。
3. プレビュー画像を Vision 対応 Ollama モデルで解析し、結果を表示できる。
4. 選択キャンセル、対象ウィンドウ終了、キャプチャ失敗、Ollama 停止、非対応モデル、解析キャンセルでアプリが異常終了しない。
5. 複数回キャプチャ・解析しても操作でき、前回のリソースが適切に解放される。
6. 既存 AI チャット、RSS / GitHub Releases 収集、通知・Worker の動作に回帰がない。
7. キャプチャ画像が意図せず DB・ファイル・ログに永続化されない。
8. Debug / Release のビルドが既存の構成に従って通る。既存テストを実行し、必要なテストを追加する。

環境依存で自動検証できない項目は、**手動検証手順と未確認事項**を明記してください。ゲーム画面は追加の任意検証とし、MVP 完了条件にしません。
