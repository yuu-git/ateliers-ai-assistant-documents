# Codex 改修指示 — 画面監視の複数セッション対応（MVP 後の基盤拡張）

## 0. 目的と進め方

Ateliers AI Assistant の Phase 7（単一画面監視・AI コメント MVP）は完了扱いとする。今回は **複数の独立した画面監視セッション**を作成・操作できるように、既存の単一セッション前提を拡張する。将来の差分検出・監視別プロンプト・通知などを実装する前に、セッション単位の境界を整えることが目的であり、Vision 精度改善や高度な解析機能は含めない。

**最初に最新コードとドキュメントを調査し、現行の単一セッション依存箇所、推奨設計、互換性、検証計画を報告して承認を待つこと。承認前にコード・文書を変更しない。** 技術的な制約が判明した場合は代替案を報告し、無断でスコープを広げない。

## 1. 既存実装の確認事項

- `phase7-implementation-status.md`、`phase7-codex-implementation-instructions.md`、Temp 管理、Worker API、モデル自動ロード／アンロード、画面監視 UI・テストの最新状態を確認する。
- 現状は Worker がユーザーセッション内で Picker／WGC／キャプチャ／Vision／トレイを所有し、Desktop を閉じても監視継続する。`Ateliers.Ai.Assistant.Windows` のキャプチャ共通処理、`ScreenMonitorService`、`ScreenMonitorContracts`、`WorkerHost`、`WorkerApiClient.Screen`、`ScreenMonitorViewModel` 等の実コードを確認する。ファイル名・構成が変わっていれば実装を優先する。
- 既存のコメント履歴は Worker メモリ保持（直近200件・本文合計8 MiB）、設定は `worker-settings.json`、画像はメモリ優先・Temp 管理の既存上限を尊重する。**これらが現在の実コードでも同じか確認する。**
- 既存の単一監視 API、設定 JSON、状態 DTO、イベント／キャンセル、Picker のスレッド所有、WGC リソースの破棄、UI の5秒程度の状態ポーリング、トレイの停止操作を調査する。

## 2. 必須ユースケース

1. **異なる対象を同時監視**：例として Chrome とタスクマネージャーを、それぞれ別周期・別プロンプト・別モデルで監視する。
2. **同一対象を独立して二重監視**：同じウィンドウまたはディスプレイを、監視Aと監視Bで別設定にして監視する。画像取得を共有・最適化する必要はない。**同じ対象であることを理由にセッションを統合・拒否しない。**
3. **独立操作**：Aの開始・停止・対象変更・エラーがBへ波及しない。UIを閉じてもWorker内の監視は続き、再起動したUIで一覧・状態・コメントを復元表示できる。
4. **監視設定**：セッションごとに表示名、対象、モデル、周期（既存候補10/30/60/120/300秒）、プロンプト、開始／停止状態を扱う。名前は識別用であり画像内容の推測に使わない。
5. **複数監視の見通し**：一覧で各監視の名前・対象・状態・次回実行・最終解析・エラーを確認し、選択した監視の設定とコメント履歴を表示する。監視の追加・削除を提供する。

## 3. セッション設計・永続化

- Worker が監視セッションの唯一の管理主体となる。セッションごとに不変の `MonitorId`（GUID 等）を持たせ、キャプチャセッションID／対象ID／コメント／状態／キャンセルトークン／周期制御を分離する。
- **監視定義（名前・モデル・周期・プロンプト）は永続化候補**とする。対象ハンドル、GraphicsCaptureItem、実行中状態、画像、コメント履歴は原則永続化しない。Worker 再起動時は全監視を停止・対象再選択が必要な状態から開始し、無断再開しない。
- 既存の単一監視設定がある場合、**初回起動時に1件の監視定義へ移行**する方法を設計する。既存ユーザーの設定・コメント・操作が不必要に失われないようにし、設定移行は再実行可能かつ失敗時に安全であること。移行後の旧APIの扱い（互換アダプター／明示的なプロトコル更新）を報告する。
- 削除時は対象取得・解析を停止／キャンセルし、リースとWGC資源を解放してから定義・コメントを削除する。処理中の削除・停止・対象変更・UI再接続の競合を扱う。
- 同一対象の重複選択を許可する。ただし、OS API 上の取得可能性・同時Picker操作・対象消失などの制約を実機で検証する。Picker 操作は競合させず逐次化する。

## 4. スケジューリングとリソース制御

- **複数監視の登録・稼働は可能にするが、Vision 推論は初期実装では Worker 全体で最大1件**とする（公平な実行順・飢餓防止を考慮）。同時 Ollama 呼び出しの並列化は非対象。
- 各監視は独立周期を持つ。周期到来時に全体の推論枠が埋まっていれば、その回をスキップして記録する。**無制限キュー、追いつき実行、遅延ジョブの積み上げをしない。** 一つの監視が長時間枠を占有した場合のタイムアウト／キャンセル／次監視への進行を設計する。
- 同一対象を二重監視しても、セッションごとに独立した画像・コメント・設定を扱う。最適化目的のフレーム共有・複数画像同時送信は今回不要。
- モデル自動ロード設定、AI一時停止、モデルの使用中保護と自動アンロードは **Worker全体の監視セッション集合**に基づき判定する。Aを停止してもBが使用中のモデルを解放しない。すべて停止したら既存の解放方針へ戻す。
- Temp の既存のプロセス全体容量上限・セッション別保持上限・一括リースを維持する。複数監視で上限に達したら安全に失敗／スキップし、他セッションの使用中画像を削除しない。
- 初期の同時監視数は **2件を最低受入条件**とし、設計は固定2件にしない。現実的な安全上限（例：最大4件）を設ける場合は、根拠・設定方法・上限時のUI挙動を事前提案する。PCスペック無視の無制限並列処理は要件ではない。

## 5. UI と Worker API

- 既存「画面監視」画面を拡張し、**監視一覧＋選択中監視の設定・コメント**を基本とする。新しい大規模画面体系は不要。現在の画面解析（Phase 6）やAIチャット等は変更しない。
- 追加・名前変更・削除・対象選択・開始・停止・設定保存を **MonitorId指定**で行う。誤って別監視を停止／削除しない。対象選択キャンセル時は当該監視の既存対象を維持する。
- API は一覧取得・個別状態・コメント・設定変更・開始停止・削除を監視IDで区別する。既存のWorker認証／バージョン管理／JSONシリアライズ規約を尊重する。UI再接続時に全監視の状態を復元表示する。
- トレイは **「全監視を停止」**を最低限提供し、監視中件数が分かるようにする。個別停止メニューは既存構成に無理なく追加できる場合のみ。トレイが利用できないときの安全動作は現行方針を維持する。
- コメント履歴は監視IDで分離。総保持量は既存のWorker全体メモリ上限を守り、監視ごとの件数上限と全体上限の適用順序を明確化する。履歴をDBへ保存しない。
- ログへ画像・画面テキスト・機密ウィンドウタイトル・プロンプト本文を記録しない。診断は監視ID、状態遷移、時間、スキップ理由、エラー種別などに限定する。

## 6. 非対象（今回実装しない）

- Vision モデルの品質改善、画像最大解像度変更、プロンプト自動最適化。
- 前回画像との差分検出、複数時点画像の同時推論、複数監視の画像をまとめた横断解析。
- GPU/CPU監視APIの追加、イベント検出・自動通知・音声出力・録画・履歴DB保存。
- 複数モデルの同時推論、GPUリソースの高度な動的配分、独立したCapture AgentやWindows Serviceの追加。
- 既存RSS/GitHub収集・通知画面の再設計。

## 7. テスト・受入条件

少なくとも以下を自動テストと実機検証で確認する。

1. 監視A（Chrome）とB（タスクマネージャー）を同時稼働し、コメント・周期・状態が混線しない。
2. **同じウィンドウをA/Bで選択**し、異なるプロンプト・モデル・周期を適用できる。モデルが利用可能な場合、それぞれのコメントが対応する設定で生成される。
3. Aだけ停止・削除・対象変更してもBは継続する。対象消失／取得失敗も他監視へ波及しない。
4. 重い推論が周期を超過しても全体同時推論数1、キュー無制限増加なし、スキップ回数が説明可能である。公平性と停止応答を確認する。
5. Desktop終了後の2監視継続、再起動Desktopで一覧・コメント再表示、Worker再起動後は自動監視しない。
6. 単一監視設定からの移行、既存設定の保持、失敗時の安全性、Debug/Release分離、Worker APIバージョン不一致時の扱い。
7. モデル自動ロードOFF、AI一時停止、異なる／同一モデルの使用中保護、自動アンロード、Temp容量制限、リース解放。
8. 同時Picker操作、選択キャンセル、ウィンドウ終了、画面ロック、停止・削除・Worker終了競合、トレイ全停止。
9. 既存Phase 6画面解析、Phase 7単一監視、RSS/GitHub収集、チャット、既存テストの回帰。

**完了条件**：少なくとも2件の独立監視（同一対象／別対象の両方）が成立し、Worker終了・UI再接続・資源管理・設定移行が安全に動作する。Visionコメントの意味的な正確さは今回の合否基準にしない。

- 画面監視仕様、Worker/API、モデル管理、Temp運用、利用手順、テスト結果を更新する。

## 9. 最初の回答（承認ゲート）

実装前に次を報告し、承認を待つこと。

1. 現行の単一セッション依存箇所と、影響するAPI／設定／UI／Worker／Temp／モデル管理。
2. 推奨する複数セッションの所有権・状態遷移・永続化／旧設定移行方式。
3. 推論全体1件のスケジューラ、スキップ・公平性・キャンセル・モデル保護の設計。
4. 同一対象を2件監視する実機上の制約と、Picker競合対策。
5. UIの最小変更案、監視数上限、テスト計画、未決定事項。

承認後に実装・テスト・文書更新を進めること。構成変更や新しい永続化基盤が必要になった場合は、その理由を先に相談すること。
