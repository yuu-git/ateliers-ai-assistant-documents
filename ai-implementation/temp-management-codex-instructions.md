# Codex 指示書：アプリ専用 Temp 管理基盤（Phase 6 完了後の横断改善）

## 目的と実施タイミング
Ateliers AI Assistant の画面キャプチャ、将来の継続画面監視・画像比較・音声生成に備え、アプリ専用の一時データ管理を設計・必要最小限で実装する。
**Phase 6 の作業完了後**に着手すること。今回の主眼は Temp 管理であり、Phase 7 の定期監視・AI コメント、音声生成、画像差分アルゴリズム自体は実装しない。

## 0. 先に既存実装を調査し、設計案を報告
- 現在の AppData（Local/Roaming、Debug/Release 分離）、Worker と UI のプロセス構成、ログ、設定、DI、画面キャプチャ、画像送信、既存のファイル管理サービスを確認する。
- Phase 6 で画像がメモリ／ディスクのどちらに保持されるか、所有者とライフサイクルを確認する。
- `ateliers-ai-assistant-documents` のロードマップ・アーキテクチャ・実装規約を確認する。
- **既存の仕組みを再利用**し、重複した Temp 管理を作らない。既存実装に大きな影響がある場合は、変更案と移行方針を先に報告し、承認を待つ。

## 1. 基本原則
1. 一時データは原則 `%LOCALAPPDATA%` 配下の**アプリ専用領域**に置く。実際のパス・Debug/Release 分離は既存のパス規約に合わせる。Roaming や OS 共通 Temp を無制限の保管場所にしない。
2. **メモリで完結できるデータはディスクに書き込まない**。画像差分計算や単発 Vision 送信はメモリ処理を優先する。
3. ディスク保存が必要な場合のみ、用途別に分離する（例：`Temp/Capture`、`Temp/Audio`、`Temp/Work`）。実際の構成は過剰に細分化しない。
4. Temp はキャッシュ／作業データであり、永続的な記事・通知・ユーザーが保存を明示した成果物と区別する。後者は自動削除しない。
5. ファイルの削除対象は**管理対象のアプリ専用 Temp 配下のみ**。パス正規化・配下判定を行い、任意パスやシンボリックリンク／再解析ポイント経由の範囲外削除を防ぐ。ディレクトリ全削除より管理対象の個別削除を優先する。

## 2. 複数時点の画像を扱えること（重要な将来要件）
将来、同一の監視対象について「60秒前・30秒前・現在」の3枚など、複数時点の画像を**同一の AI 解析要求**に渡してコメント生成する可能性がある。Temp 管理はこれを阻害してはならない。

- キャプチャを識別する ID、監視セッション／対象の識別子、取得時刻（UTC）、保存先またはメモリ参照、サイズ等のメタデータを扱える設計とする。対象のウィンドウ名等、不要な個人情報をファイル名に含めない。
- **複数画像を時系列で選択・取得するための契約**を検討する。例：指定時刻に最も近い画像の選択、同一セッション内の時刻順列挙。ただし Phase 7 のキャプチャスケジューラや画像比較ロジックは作らない。
- AI 解析に使用する複数画像は、**一括して使用権（リース／参照カウント等）を取得**でき、解析完了またはキャンセル時に確実に解放できること。解析中の削除・上書きを防止する。
- 画像の時間差を厳密に30秒と仮定しない。キャプチャ遅延や欠損を想定し、実際の取得時刻を使用する。
- 画像が不足している場合、別セッションの画像しかない場合、画像が破損・消失している場合の扱いを明示する。
- Ollama に複数画像を渡す API の具体的な拡張は今回必須ではない。既存の画像送信処理に影響がある場合は、**別途変更提案**に留める。
- ディスク上の保持世代数は「直近3枚固定」にしない。解析頻度・時間幅に応じて設定可能な保持ポリシーを設計する。実装の初期値は実測を踏まえて提案する。

## 3. クリーンアップと容量制限
- **世代数・保持期間・総容量**の複数条件を組み合わせる。設定の初期値（例：数世代、24時間、数百 MB）は仮置きであり、キャプチャサイズ・運用を確認して決める。
- 削除は古く、使用中でないものから行う。画像の参照中・音声再生中・書き込み途中のデータを削除しない。
- **上限を超えても使用中ファイルを強制削除しない**。回収不能な場合は新規生成の抑制／失敗通知／ログ記録で対処し、無制限に増やさない。
- ファイル書き込みは可能な範囲で一時名からの確定処理などを用い、未完成データを解析対象にしない。
- 起動時、処理完了時、必要に応じた定期清掃、正常終了時に回収する。クラッシュ・強制終了では終了処理が走らないため、**次回起動時の残存ファイル回収**を必須とする。
- 清掃失敗はログに記録し、他機能や Worker を巻き込んで停止させない。リトライは無限ループにしない。

## 4. UI と Worker の共存・所有権
- UI が閉じても Worker が稼働する構成を尊重する。**UI 終了を理由に共有 Temp 全体を削除しない**。
- プロセス単位／監視セッション単位など、所有範囲を明確にする。プロセス間共有が必要な場合、単一プロセス内の参照カウントだけで安全だとみなさない。
- プロセス間で使用中判定を実現する方式（専用作業ディレクトリ、ロック、メタデータ、所有プロセス、期限付きリース等）を比較し、最小限で堅牢な方式を選ぶ。**PID だけを根拠に生存判定しない**。
- 異常終了した所有者のファイルは、他プロセスが使用中でないことを確認した上で回収する。共有管理が不要なら、用途／プロセスの分離で簡素化してよい。

## 5. セキュリティ・プライバシー
- キャプチャ画像には機密情報が写る可能性がある。**既定では永続保存しない**。保存が必要な場合も最小期間・最小容量とする。
- ログに画像データ、画面上の機密テキスト、音声本文を不用意に出力しない。パス・識別子のログも必要最小限にする。
- ディスクへの一時保存は既存ユーザープロファイルのアクセス制御に従い、追加の公開・共有設定を作らない。

## 6. 実装範囲とテスト
- 既存のサービス構成に沿って、必要な Temp パス管理、生成／登録、取得、使用中保護、解放、削除、清掃を実装する。**汎用キャッシュフレームワークやプラグイン基盤は導入しない**。
- Phase 6 の既存キャプチャがメモリ完結なら、無理に Temp へ保存する改修をしない。将来の複数時点画像を保持できる契約・実装可能性を確保する。
- 最低限のテスト：世代・期限・容量超過、使用中保護、複数画像の一括取得と解放、取得時刻順、キャンセル／例外時解放、UI 終了と Worker 継続、異常終了残存ファイルの清掃、削除範囲の逸脱防止、Debug/Release 分離。
- ファイルシステム操作はテスト可能な境界を設ける。不要な設定 UI やユーザー操作を追加しない。

## 7. ドキュメントと完了報告
- 設計判断、実際の Temp ディレクトリ、用途別保持ポリシー、クリーンアップ契機、複数時点画像の扱い、既知の制限を `ateliers-ai-assistant-documents` の適切な場所に記載する。
- 既存ロードマップに新フェーズを勝手に追加しない。Phase 6〜7 を支える横断的改善として記録する。
- 完了時は変更ファイル、採用方式、既存 Phase 6 への影響、テスト結果、Phase 7 に残す作業、容量上限時の動作を報告する。

## 8. 作業手順
1. **現状調査と実装案を先に提示**する。既存実装との衝突や、UI／Worker 間共有方式など重要な未確定事項があれば質問し、承認を待つ。
2. 承認後、最小限の変更を実装・テストする。
3. ドキュメントを更新し、結果を報告して終了する。

**今回の対象外：** Phase 7 の自動キャプチャ、画面差分検出アルゴリズム、AI コメント自動生成、TTS・音声再生、汎用 Web 監視、AI 管理コンソール。
